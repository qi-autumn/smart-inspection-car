一句话结论

先把你的流程图补完整
你画的方向完全对：采集语音 → 转成文字 → 让大模型把文字判成规范指令 → 下发。 但要修正两点：①「语音转文字」是 ASR 语音识别模型/服务干的活，不是让 Qwen 这类文本大模型去"听"音频；② 大模型只负责翻译意图，绝不能让它直接开车——它输出的 JSON 必须先过项目已有的命令白名单和参数范围校验，再交给既有的 POST /command。而且所有 AI/ASR 调用都放在 PC 后端 :8000，密钥不能进网页、不能进 APP。

你以为的 3 步

语音→语音解析模块→文字→AI 判含义→规范指令

问题：把"听"和"懂"混成一个模块；少了「谁校验」「谁执行」「谁回报」。

实际要落的 7 跳

① 采集② ASR 转写③ LLM 解析④ 白名单校验⑤ 任务排程⑥ /command⑦ 反馈/播报

前 2 跳解决"听见没有"，第 3 跳解决"是什么意思"，第 4~6 跳保证"不会乱开"，第 7 跳解决"用户知道结果"。

四个直答：
  • Qwen 能判定文字吗？能，而且很合适。用它的 Function Calling / 结构化 JSON 输出把"让 3 号车往东慢慢开三秒"填成固定槽位，别让它自由发挥写正文。
  • 语音转文字有大模型可调用吗？有。2026 年阿里云百炼提供 Qwen3-ASR-Flash（可 OpenAI 兼容方式调用）、Fun-ASR、Paraformer 实时识别等；也可以完全本地跑 SenseVoice-Small / FunASR / Whisper。不是二选一，是三条路线，见 §5 方案切换。
  • 网页版支持语音采集吗？技术上支持，但当前项目会被卡住：浏览器只允许 HTTPS 或 localhost 调麦克风，而项目是 http://<局域网IP>:8000；并且 Chrome 内置的 webkitSpeechRecognition 要连 Google 云，国内网络基本用不了。正确做法是「网页录音 → 上传后端 → 后端 ASR」，且要先解决 HTTPS。
  • APP 支持吗？支持，走鸿蒙原生 @kit.CoreSpeechKit 的 speechRecognizer（端侧识别、数据不上云）；但 module.json5 现在只声明了 INTERNET，要补麦克风权限和运行时申请。而且端侧语音识别不支持 DevEco 手机模拟器，需要真机。

生活比喻：餐厅点菜

为什么必须分成几个人

你说"来一份不太辣的牛肉面，快点"——这句话要变成厨房能执行的单子，中间是四个人接力：

角色干什么项目里对应
耳朵把声波收下来，变成一段音频，还没理解任何意思浏览器 getUserMedia / APP MICROPHONE 权限
速记员只管逐字记："来一份不太辣的牛肉面，快点"。不需要懂菜ASR：Qwen3-ASR / Paraformer / SenseVoice / Core Speech Kit
点单顾问看懂意思，翻成菜单编号：#27 牛肉面 / 微辣 / 加急。不需要会听LLM：Qwen + Function Calling / JSON Schema
收银台核对菜单上真的有 #27、辣度只能是固定档位、金额不超限；没有就打回CMD_WHITELIST、build_move_paras()、devices.json、冻结判断
后厨只认标准化单子，按单做菜，做完回一句"已出餐"POST /command → IoTDA → 小车
最容易犯的错：让"点单顾问"直接冲进后厨开火（让 LLM 直接生成 vx/vy 或直接调华为云），或者把"速记员和顾问"合成一个人（指望一个通用文本大模型同时听音频、理解意图、输出指令）。前者会出安全事故，后者在国内网络/延迟/可调试性上都很难受。

还有一个细节：播报（路线图⑦验收里的"播报执行结果"）是反方向的另一条线——文字 → 语音（TTS）。网页用 speechSynthesis、APP 用 Core Speech Kit 的 textToSpeech、或后端调 qwen3-tts/CosyVoice 生成音频。它是锦上添花，不属于控车主链路。

文件与接口：规范指令长什么样

AI 输出的唯一合法形状

项目里"规范指令"其实是两层

层长什么样谁产生 / 谁消费
L1 业务命令{"device_id":"car_003","cmd":"MOVE","angle":90,"speed":35}
白名单 FORWARD / BACK / LEFT / RIGHT / MOVE / STOP；speed 0~100 整数；MOVE 的 angle 0=正北、顺时针 0~360		网页摇杆 / APP 产生 → POST /command 消费 → build_move_paras() 转成 vx/vy
L2 任务计划⑦ 新增{"device_id":"car_003","plan":[{"cmd":"MOVE",...,"duration_ms":3000},{"cmd":"STOP"}]}LLM 产生 → /ai/command 校验+排程 → 逐条调 /command

duration_ms 是编排层字段，不是 /command 的参数：后端定时器到点再发下一条，绝不能把它塞进现有接口假装支持。设备短名 car_003 由 resolve_device_id() 补全成云端完整 ID。

建议的 POST /ai/command 契约

// 请求（文字模式，先做这个）
POST http://127.0.0.1:8000/ai/command
Content-Type: application/json

{ "text": "让3号车慢慢往东开三秒然后停",
  "device_id": "car_003" }

// 请求（语音模式，后端自己调 ASR；也可直接传 text 跳过 ASR）
{ "audio_b64": "<wav 16k 16bit 单声道>", "mime": "audio/wav",
  "device_id": "car_003", "confirm": true }

// 响应：steps 必须来自 /command 的真实返回值
{ "ok": true,
  "transcript": "让3号车慢慢往东开三秒然后停",
  "plan": [ {"cmd":"MOVE","angle":90,"speed":35,"duration_ms":3000},
            {"cmd":"STOP"} ],
  "steps": [ {"ok":true,"command_id":"..."}, {"ok":true,"command_id":"..."} ],
  "reply": "已让 3 号车以 35% 速度向东行驶 3 秒并停车" }

LLM 的 System Prompt 要点

你是车队指令解析器，只输出 JSON，不输出解释文字。
可选车辆（来自 devices.json）：car_001..car_005
允许 cmd：FORWARD/BACK/LEFT/RIGHT/MOVE/STOP
speed：0~100 整数；angle：0~360（0=正北，顺时针）
"慢慢"=35，"快点"=70，"全速"=100
"往东"=90，"往北"=0，"往南"=180，"往西"=270
输出形状：
{"device_id":"car_003",
 "plan":[{"cmd":"MOVE","angle":90,"speed":35,
          "duration_ms":3000},{"cmd":"STOP"}],
 "say":"已让3号车向东慢速行驶3秒"}
信息不足（没说车号/没说动作）时输出
{"need_clarify":"请问要控制哪台车？"}
禁止：输出代码、URL、自由文本、编造车号、生成白名单外的 cmd。

工程上更稳的做法是别靠提示词"求"它守格式，而是用 Function Calling 或 response_format: {"type":"json_object"} / JSON Schema 把输出形状锁死（Qwen 百炼的 OpenAI 兼容端点支持），解析后仍然要在服务端再校验一遍。

配置文件与安全边界

server/ai_config.json   （新建，照 cloud_config.json 的模式；字段名示意，不写任何真实密钥）
{
  "base_url": "https://dashscope.aliyuncs.com/compatible-mode/v1",
  "api_key":  "YOUR_CREDENTIAL",
  "llm_model": "qwen-plus",
  "asr_model": "qwen3-asr-flash"

路线图⑦第 4 条明确要求「key 存配置文件，不入库不入仓」。当前工程还没有 .gitignore，而 server/cloud_config.json 里已有明文 AK/SK——新增 AI 配置时顺手补一份 .gitignore（至少忽略 server/*config.json、*.p12），或干脆用环境变量 DASHSCOPE_API_KEY。本页没有写入任何账号密钥。

为什么密钥只能在后端：网页里的 JS、APP 里的 ArkTS 都运行在用户设备上，任何写死在里面的 key 都能被直接翻出来。现有架构里后端 :8000 是唯一同时持有华为云 AK/SK 和所有业务规则的地方，AI 的 key 也放这里，前端只把"文字或音频"交给它。

网页：能采集，但项目现在的访问方式会直接被浏览器拦住

路线做法结论
A. 浏览器内置识别
webkitSpeechRecognition		几行 JS 直接出文字，零后端不推荐 Chrome/Edge 的识别要把音频送到 Google 云，国内普通网络直接 network 错误或静默结束；Firefox 不支持
B. 录音上传后端 ASR
getUserMedia + MediaRecorder		网页录一段 → POST /ai/command 带音频 → 后端调 ASR → LLM推荐 和现有架构一致，密钥只在后端，网页/APP 可共用同一个 ASR 接口

硬闸门：安全上下文。只有 https://…、http://localhost、http://127.0.0.1 才允许调麦克风。你现在用 http://192.168.1.x:8000 从别的设备访问大屏，浏览器里 navigator.mediaDevices 会是 undefined，按钮点了毫无反应——不是代码写错。所以：

  • PC 本机自测：用 http://127.0.0.1:8000 打开，可以采。
  • 手机 / 别的电脑访问：先按 HTTP 与 HTTPS 那份教材把局域网链路升成 HTTPS（自签证书内网可用）。
  • 必须由用户点击触发录音请求，不能在页面加载时自动调；权限被拒过一次会被浏览器记住，要去站点设置手动重置。
  • MediaRecorder 默认常输出 webm/opus，而多数云 ASR 要 wav / pcm 16k 16bit 单声道——前端用 AudioContext 重采样，或后端用 ffmpeg/soundfile 转码。

涉及文件：web/monitor.html 或新建 web/ai_chat.html；后端 server/app.py 新增 /ai/command。APP 里内嵌的那些 Web 页面（admin/monitor）跑在鸿蒙 Web 组件里，不等于完整浏览器，别指望网页的 SpeechRecognition 在 APP 内嵌页也照样能用。

APP：支持，走鸿蒙原生 Core Speech Kit，不要走网页那套

// 1) entry/src/main/module.json5 —— 当前只有 INTERNET，要补：
"requestPermissions": [
  { "name": "ohos.permission.INTERNET" },
  { "name": "ohos.permission.MICROPHONE",
    "reason": "$string:microphone_reason",
    "usedScene": { "abilities": ["EntryAbility"], "when": "inuse" } }
]
// resources/base/element/string.json 里补 microphone_reason 文案

// 2) 运行时动态申请（abilityAccessCtrl），用户授权后才能开识别

// 3) 端侧识别（@kit.CoreSpeechKit）
import { speechRecognizer } from '@kit.CoreSpeechKit';
//   createEngine({language:'zh-CN', extraParams:{locate:'CN', recognizerMode:'short'}})
//   → setListener() → startListening() → on('result') 拿到文字
//   → finish() / shutdown() 释放引擎

// 4) 把文字交给后端，其余全在 PC 完成
FleetClient.postAiCommand(text, this.boundDeviceId)
//   → POST http://<PC局域网IP>:8000/ai/command
  • Core Speech Kit 的 ASR/TTS 是端侧运行、数据不上云、可离线，短语音模式适合"一句话指令"（≤60s），还能配热词提高"car_00X / 3 号楼"这类专有名词的识别率。
  • 大坑 有资料明确指出端侧语音识别不支持模拟器，必须用真机；DevEco 虚拟手机也没有真实麦克风。所以先在模拟器里用打字输入把 /ai/command 后半段跑通，真机再补语音采集。
  • 另一种统一起见的做法：APP 用 AudioCapturer 只采 PCM，上传后端 ASR——网页和 APP 就共用一条识别链路，代价是多一次上传、多一趟网络。
  • 具体 API 名称、online 等参数取值以你本机 DevEco / SDK 版本的官方文档为准，不同版本示例略有差异。

"还是本地解析？" —— 也可以在 PC 上完全离线转写

方案大概体量适合
SenseVoice-Small（ONNX / sherpa-onnx）约 200~250MB，CPU 上接近实时短指令、 fastest 演示、无公网环境；纯转写、不带标点润色
FunASR / Paraformer（本地服务化）数百 MB，中文准确率好想要 VAD/标点/热词一整套，愿意多装依赖
Whisper（tiny/small）75MB 起，CPU 慢一些多语种、生态成熟、原型最快
Qwen3-ASR 0.6B 本地权重约 0.8~1.5GB中文转写质量优先，但纯 CPU 上不快

"本地解析"这个词要拆开看：ASR 模型可以本地跑（上面这些），LLM 也可以本地跑（Ollama / llama.cpp 起个 Qwen 小模型），但两者都不必要。教学项目里最省事的是云端 ASR + 云端 LLM，因为路线图已经允许"中转站 base_url + key"，且你的后端本来就联网。只有「断网演示 / 隐私 / 不想花钱」时才值得上本地模型。

给初学者的最小可行顺序（别一上来就调麦克风）

  1. 阶段 0：纯文字。只做 POST /ai/command 收 text → Qwen 出 JSON → 白名单校验 → 调 /command → 返回真实 steps。用 curl 在 PC 上验收，不碰任何语音。这一步能把 80% 的坑提前暴露。
  2. 阶段 1：网页录音。PC 用 127.0.0.1 打开，MediaRecorder 录一段上传，后端接云 ASR（Qwen3-ASR-Flash / Paraformer）。
  3. 阶段 2：HTTPS。要真机浏览器 / APP 内嵌页也能录音，再按教材升级 HTTPS。
  4. 阶段 3：APP 原生语音。真机 + Core Speech Kit + 麦克风权限，把文字丢给同一个 /ai/command。
  5. 阶段 4：播报与日报。TTS 念结果；用 /track + commands.log 让 LLM 写巡检日报。
关键心法：ASR 和 LLM 是可以随时替换的两个"插件"，中间契约就是那串文字和那个 JSON。先 fixed 契约，后面网页换 APP、云 ASR 换本地模型，都不用改执行链路。

示例：一句话在每一跳变成什么

跳数据说明
① 音频[PCM 16k 16bit 单声道, 约 2.5s]网页 MediaRecorder / APP Core Speech Kit / AudioCapturer
② 文字"让3号车慢慢往东开三秒然后停"ASR 输出，建议原样存进审计日志，便于回溯误识别
③ JSON{"device_id":"car_003","plan":[{"cmd":"MOVE","angle":90,"speed":35,"duration_ms":3000},{"cmd":"STOP"}],"say":"…"}Qwen Function Calling / JSON Schema 锁形状
④ 校验后device_id ∈ devices.json ✓ / cmd ∈ 白名单 ✓ / speed 35 ✓ / angle 90 ✓ / 未冻结 ✓任何一项不过 → 返回 need_clarify 或拒绝，不下发
⑤ 排程t=0 POST /command {MOVE,90,35}；t=3.0s POST /command {STOP}后端定时器；异常/用户急停要能取消后续步骤
⑥ 既有链路build_move_paras() → vx=0.35, vy=0 → CreateCommand → MQTT 8883 → 车和摇杆走的是同一条路，不新开协议
⑦ 反馈"已让 3 号车向东慢速行驶 3 秒并停车" → 文字 / TTS必须基于 /command 真实返回值；某步 502/403 就如实说失败
6

常见坑

按踩到的概率排序

安全把大模型当成"司机"

让 LLM 直接输出 vx/vy、直接调 IoTDA，或让它自由生成 cmd，等于把白名单拆了。幻觉、单位错、车号编造都会变成真车乱跑。模型只能填槽，校验和执行权永远在后端。

安全API Key 写进前端

网页 JS 里的 api_key、ArkTS 里写死的 key，任何人都能翻出来。放 server/ai_config.json 或环境变量；工程现在还没有 .gitignore，顺便补一份。

网页HTTP + 局域网 IP 调不了麦克风

http://192.168.1.23:8000 不是安全上下文，navigator.mediaDevices 直接是 undefined，静默失败无报错。PC 改 127.0.0.1，跨设备访问要 HTTPS。

网页Chrome 内置识别连不上 Google

webkitSpeechRecognition 的识别在云端完成，国内常表现为 onstart 触发后 onerror: network 或直接静默 onend。别拿它当正式方案；TTS（speechSynthesis）反而本地可用，两者别搞混。

网页权限被拒后"刷新也没用"

浏览器按域名记住麦克风授权，拒绝过就不再弹窗；且必须由用户点击触发，页面加载时自动请求会被拦。调试时去地址栏站点设置手动重置。

APP只声明了 INTERNET

CarFleet/entry/src/main/module.json5:13~17 目前只有网络权限。要补 ohos.permission.MICROPHONE、reason 文案、usedScene，还要在运行时用 abilityAccessCtrl 动态申请。

APP模拟器上语音功能"怎么都不动"

端侧语音识别需要真机，DevEco 虚拟手机没有真实麦克风。先在模拟器里用打字输入验收 /ai/command，真机再接 Core Speech Kit。另外 APP 内嵌的 Web 组件不是完整浏览器。

协议"开三秒"车不会自己停

现有 /command 一次一条、没有时长字段。必须后端排程到点补 STOP，并支持中途取消；否则 LLM 说完"三秒"，车会一直按上一速度跑下去（这正是之前大屏上遇到过的"一直执行上一个命令"）。

数据"去 3 号楼"没有坐标

项目里没有地图点位表。LLM 不知道"3 号楼"在哪，只能编一个坐标。要补 points.json 做名称→(x,y) 映射，并在系统提示词里把可选点位列表喂给它。

数据车号靠模型猜

"3 号车 / 第三台 / 那辆红的"要映射成 devices.json 里真实存在的 ID；把车型清单连同名称/颜色一起放进提示词，解析后用 resolve_device_id() 复核，别让模型凭空造 car_009。

音频录音格式对不上

浏览器常给 webm/opus，云 ASR 常要 wav/pcm 16k 16bit 单声道。前端 AudioContext 重采样或后端转码；长音频还要注意云服务的大小/时长限制与异步转写模式。

反馈"已执行"是模型想象出来的

播报内容必须由 /command 的真实返回值拼出来。设备离线（502）或冻结（403）时要如实说失败，别把 LLM 的 say 字段当执行结果；注意别和项目里的"乐观回显"混为一谈。

架构把 AI 塞进实时闭环

ASR 0.5~2s + LLM 1~3s 是一次性"任务编排"的延迟，不是控制周期。别让 AI 每 200ms 参与一次决策，也别把 AI 推测写进 STATE_CACHE 或影子轨迹——轨迹只记真实位置变化，否则回放数据会被污染。

工程密钥入仓 / 模型名没开通

百炼按业务空间逐个开通模型，直接调没开通的模型名会报"模型不存在/无权限"。配置文件不要提交；base_url 用可配置的兼容端点，方便在中转站和官方端点之间切换。
