先给结论

一句话：HTTPS 不是另一种协议，就是 HTTP 外面套了一层 TLS。请求方法、路径、JSON 报文、状态码全都没变，变的只是"这段字节在网线里是明文还是密文"。所以升级时业务逻辑一行都不用改，改的只是"怎么起服务、客户端怎么连"。

生活比喻：HTTP 像寄明信片，路上谁都能看清内容；HTTPS 像把同一张明信片装进带锁的保险箱，且收件人要先出示身份证（证书）证明"我确实是那台服务器"。信的内容没变，运输方式变了。

TLS 带来的三件事

  • 加密：中间人看不到 JSON 里的位置、命令、token
  • 身份认证：证书证明"你连的真是那台后端"，防冒充
  • 完整性：传输中被篡改会被发现

它不解决什么

  • 不解决"密码太简单"（admin/admin123 仍是弱口令）
  • 不解决"服务端本身被攻破"
  • 不解决"明文 HTTP 页面里混了 HTTPS 请求"之外的混合内容问题

项目现状盘点：哪里是 HTTP、哪里已经是加密的

先别急着升错地方

你说"当前项目中都有涉及到"，这个判断是准确的。但要先分清：加密的部分其实不在客户端这一段。

链路协议加密证据（源码 / 配置）
APP ↔ 业务后端HTTP/1.1 明文 :8000否FleetClient.ets : 58、90、144 全部是 http://${host}:${port}
网页 ↔ 业务后端HTTP + ws:// 明文 :8000否monitor.html 的 fetch("/command")、new WebSocket(ws://...)；admin.html 的相对路径 fetch
后端 ↔ 华为云应用侧 APIHTTPS是cloud_config.json 的 endpoint 本身就是 https://9dcc8e0e...iotda-app.cn-north-4.myhuaweicloud.com；SDK 用 AK/SK 签名
模拟小车 ↔ IoTDAMQTT over TLS 8883是car_mqtt_client.py : 258~263 的 ssl.create_default_context() + tls_set_context()。注意：这是加密的 MQTT，不是 HTTPS
后端 → 模拟器 /stateHTTP 明文 127.0.0.1:808N否本机回环调试口，不出网卡，风险极低
结论：所谓"把项目中的 HTTP 升级为 HTTPS"，准确地说只指局域网里"客户端（网页 + APP）↔ 业务后端 :8000"这一段。云端 SDK 那段早就是 HTTPS 了，设备那段是加密 MQTT，都不用动；本机 127.0.0.1 旁路也无升级必要。
为什么当前敢用明文：教学项目跑在同一个 WiFi 局域网里，数据只是小车坐标和演示用 token。但同一个网络里的人理论上可以抓包看到 X-Auth-Token、伪造命令、冒充后端——这正是 HTTPS 要补的缺口。
2

HTTP 与 HTTPS 的区别对照

维度HTTPHTTPS（HTTP + TLS）
本质应用层协议，直接跑在 TCP 上同一个 HTTP，中间插入 TLS 层：HTTP → TLS → TCP
默认端口80443（只是默认值；本项目升完仍可用 8000）
握手TCP 三次握手后直接发请求TCP 握手后还要 TLS 握手（协商算法、验证书、交换密钥），多 1~2 个往返
证书 / CA不需要服务端要有证书；客户端要信任签发它的 CA，否则报"证书不受信任"
数据形态明文，抓包直接读到 JSON 与 token密文，抓包只能看到 IP、端口、大致流量大小
身份验证无，可能被 DNS 劫持 / 中间人冒充证书 + 域名/IP 校验，能识别冒充
URL 前缀http://，WebSocket 是 ws://https://，WebSocket 是 wss://
性能略快首次握手多一点开销，之后对称加密几乎无感；HTTP/2、连接复用还能反超
调试curl / F12 / 抓包一目了然，教学友好需要 -k、装证书或配置代理才能看明文
项目里的取舍局域网演示、便于抓包教学、零配置若要把 APP/后台放到公网或多人共用网络，必须升级

代码视角：协议差异对业务代码是"透明"的

下面这行在项目里同时适用于 HTTP 和 HTTPS，升级后完全不用改：

// web/admin.html：相对路径，浏览器自动跟随页面自身的协议
const r = await fetch(path, {headers: hdr(), ...opts});
// web/monitor.html：发命令同理
const r = await fetch("/command", { method: "POST", ... });

只有写死完整 URL 的地方（APP 的 http://${host}:${port}）才必须改字符串。这个差别在升级时非常关键。

3

TLS 到底做了什么（简化握手）

  1. TCP 三次握手：先连上 8000 端口（与 HTTP 完全相同）。
  2. ClientHello：客户端说"我支持这些加密算法"。
  3. ServerHello + 证书：服务端选定算法，并把证书（含公钥、域名/IP、签发者）发过来。
  4. 客户端验证证书：是不是受信任的 CA 签发？有没有过期？证书里的域名/IP 和我访问的地址一致吗？这一步就是自签证书在鸿蒙 APP 上最容易失败的地方。
  5. 密钥协商：双方用非对称加密安全地商量出一个"会话密钥"。
  6. 切换对称加密：之后的 HTTP 报文全部用会话密钥加密传输（对称加密快）。

之后每一次普通请求都复用这个会话，开销很小。所以"HTTPS 很慢"在长连接/复用场景下基本不成立。

项目里已有的加密代码长什么样（可作参照）

# device/car_mqtt_client.py : 257~263 —— MQTT 的 TLS 配置（不是 HTTPS，但同一套 TLS）
try:
    ctx = ssl.create_default_context()
    mqttc.tls_set_context(ctx)                 # 用系统 CA 校验证书
    print("[MQTT] TLS: 使用系统 CA 校验")
except Exception as e:
    mqttc.tls_set(cert_reqs=ssl.CERT_NONE)      # 降级：不校验（仅调试可接受）
    mqttc.tls_insecure_set(True)

看，TLS 的接入点在代码里就是"给连接套一层 context"。Flask 侧升级也是同样的思路，只是换成 ssl_context 参数。

4

升级六步（可照着做）

本文只给方案，未改动工程

目标：把 http://PC内网IP:8000 变成 https://PC内网IP:8000，网页与 APP 都能连，ws:// 同步变成 wss://。

第 1 步 · 生成一张证书（含局域网 IP 的 SAN）
在项目根目录执行（Git Bash / OpenSSL 1.1.1+）；把 IP 换成你 PC 的实际内网地址
openssl req -x509 -newkey rsa:2048 -nodes \
  -keyout server.key -out server.crt -days 365 \
  -subj "/CN=v3-fleet-local" \
  -addext "subjectAltName=IP:192.168.1.10,DNS:localhost"

为什么必须写 SAN：现代客户端不再只看 CN，而是校验 subjectAltName。你用 https://192.168.1.10:8000 访问，证书里就必须有 IP:192.168.1.10，否则会报"证书与主机名不匹配"。

第 2 步 · 后端启动时挂上证书
server/app.py : 1079（当前原文 → 改后）
# 现在
app.run(host="0.0.0.0", port=8000, threaded=True, use_reloader=False)

# 改成（建议用环境变量控制，方便一键回退）
import os
ctx = ("server.crt", "server.key") if os.environ.get("V3_HTTPS") == "1" else None
app.run(host="0.0.0.0", port=8000, threaded=True,
        use_reloader=False, ssl_context=ctx)

关键点：flask-sock 的 /ws 跑在同一个 Flask 服务上，服务端不用改 WebSocket 代码，它自动变成 wss。端口保持 8000 完全可以，443 只是惯例不是规定。

第 3 步 · 网页端：几乎零改动（这是现成的好设计）
web/monitor.html : 130~133　web/admin.html : 183~184
// monitor.html 早就写好了协议自适应，不用动：
const proto = location.protocol === "https:" ? "wss" : "ws";
ws = new WebSocket(`${proto}://${location.host}/ws`);

// admin.html 用的是相对路径，页面是 https 时请求自动就是 https：
const r = await fetch(path, {headers: hdr(), ...opts});

只要用 https://... 打开页面，所有 fetch 自动走 HTTPS、WebSocket 自动走 WSS。没有混合内容问题（项目里没有任何写死的 http:// 资源引用）。

首次访问自签证书时，浏览器会显示"您的连接不是私密连接" → 点"高级 → 继续前往"。这是自签证书的正常表现，不是配置失败。
第 4 步 · APP 端：三处字符串 + 证书信任（真正的难点）
CarFleet/entry/src/main/ets/net/FleetClient.ets : 58、90、144
// 现在（三处都是写死的 http://）
this.baseUrl = `http://${host}:${port}`;
const resp = await req.request(`http://${host}:${port}/fleet/status`, {...});
const resp = await req.request(
  `http://${host}:${port}/track?device_id=${encodeURIComponent(deviceId)}`, {...});

// 改成（建议抽成一个常量，别改三遍）
const SCHEME = 'https';
this.baseUrl = `${SCHEME}://${host}:${port}`;

但只改字符串还不够：鸿蒙系统默认不信任自签证书，请求会直接失败。三种处理方式（按推荐度排序）：

  • 方案 A（最规范）：把自建 CA 证书放进应用资源，在 @ohos.net.http 的请求选项中指定自定义 CA（该能力以你所用 SDK 版本的 HttpRequestOptions 文档为准，常见字段名为 caPath），并在 module.json5 里确认网络安全配置允许。同时证书 SAN 必须含 PC 的 IP。
  • 方案 B（设备侧）：把这张自签 CA 装入手机/模拟器的受信任凭据（开发设备可做，不适合分发给用户）。
  • 方案 C（公网/正式）：用受信任 CA 签发的证书 + 真实域名 + 内网 DNS 指向 PC，客户端无需任何特殊配置。适合真要部署时。
  • 教学折中：APP 暂保留 HTTP，只把网页端升到 HTTPS（网页浏览器点一次"继续前往"即可），演示"HTTPS 链路"概念已经够；或按第 5 步用反向代理统一处理。

另外：APP 里内嵌管理后台的 Web 组件加载的是 /admin/view，若 APP 侧用 https，这个 URL 也要一起换；Web 组件对自签证书同样可能拦截，需要按所用 SDK 的 Web 组件证书策略处理。

第 5 步 · 本机旁路保持原样
server/app.py 的 local_fast_loop

后端 10Hz 拉 http://127.0.0.1:808N/state 是同一台机器内部的回环流量，不经过网卡、不暴露到局域网，不需要升级也不建议升级（给每台模拟器配证书只会徒增麻烦）。同理，cloud_config.json 的 SDK endpoint 已经是 https，MQTT 已是 TLS 8883，都不动。

第 6 步 · 可选：用反向代理，一行代码都不改

如果不想动 Flask 和 ArkTS，可以在 PC 上跑一个 nginx / stunnel：外部 https://PC:8443 → 本地 http://127.0.0.1:8000。优点：后端源码零改动、证书集中管理；缺点：多一个进程、WebSocket 需要显式配置 proxy_set_header Upgrade 才能转发，APP 仍要处理自签证书信任。适合只想演示"链路上锁"的场景。

7

常见坑 + 自测

常见坑

  • 自签证书没写 SAN / SAN 里的 IP 与访问地址不一致 → 证书校验失败。
  • 只改了 http→https，忘记 ws→wss（本项目已有自适应，别的地方容易漏）。
  • https 页面里引用了 http:// 的脚本或接口 → 浏览器按"混合内容"直接拦截。
  • 以为 443 是硬性要求 → 端口可自定义，本项目保持 8000 即可。
  • 以为升了 HTTPS 就等于安全 → admin/admin123、token 放内存、无速率限制等问题依旧。
  • 升级后抓包看不到明文了，教学演示时反而不好讲 —— 可以用浏览器 F12 看解密后的内容。
  • 把"MQTT over TLS"说成"HTTPS"：协议不同，只是都用了 TLS 这一层。

自测小问题

1. HTTPS 相比 HTTP，HTTP 报文本身变了吗？

没有。方法、路径、头、JSON 请求体、状态码完全一致，只是这些字节在传输前被 TLS 加密、到达后解密。所以后端 22 个路由、前端 fetch 逻辑都不用改。

2. 项目里哪些链路其实早就加密了？

后端 → 华为云应用侧 SDK（https://...iotda-app...），以及小车 → IoTDA 的 MQTT over TLS 8883。要补的只有局域网"客户端 ↔ 后端 :8000"这一段。

3. 为什么网页端升级几乎不用改代码，APP 端却要改？

网页全用相对路径（fetch("/command")）且 WS 代码已按 location.protocol 自动选 ws/wss；APP 里把完整 URL 写死成 http://${host}:${port}，还涉及系统对自签证书的信任策略。

4. 自签证书为什么必须带 SAN？

现代 TLS 客户端校验证书主体时看 subjectAltName，不再只看 CN；且校验值要与你地址栏/代码里写的主机名或 IP 精确一致。否则即使证书本身可信，也会因"名称不匹配"被拒。

5. 升级 HTTPS 之后，还有哪些安全问题没解决？

弱口令 admin/admin123、token 仅内存态且无过期、接口无速率限制、云端 AK/SK 明文放在配置文件里。加密只保护"传输途中"，不保护"两端本身"。

6. 如果只想演示概念、不想动 APP，最省事的做法是？

只给 Flask 加 ssl_context，网页用 https 打开（浏览器点一次"继续前往"），APP 暂时保留 http 走 8000 明文——但这要求后端同时监听两个协议，或者干脆演示时先不启动 APP。更干净的做法是第 6 步的反向代理：只有代理对外是 https，后端仍是 http。
