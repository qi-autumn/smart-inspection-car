项目版本全景与目录盘点

我的智能巡检小车项目里，到底有几个版本？分别是哪几个？

学习路径：总体把控 → 面 → 线 → 点　|　盘点对象：E:\Harmony\Project（12 个顶层目录） 与 E:\Harmony\CompleteProject（11-14 完整包）
一句话结论：按《V3-开发路线图》的官方口径，只有 3 个正式版本：V1 TCP 直连单车版 → V2 华为云 IoTDA 云控版 → V3 巡检车队版。但目录里实际有 12 个顶层文件夹：其中 8 个属于巡检车项目（3 个主线版本 + 4 条支线/适配 + 1 个废弃分支），另外 3 个是无关的模板/音乐课程、1 个是课堂资料。所以「几个版本」有三种数法，别只记一个数字。

1. 生活比喻：一个项目，三代车 + 一堆试车记录

把它想成一家造小车公司的样品间：
· 正式版本 = 三代正式量产车：一代用网线直连（V1）、二代换成云平台遥控（V2）、三代能管一整支车队（V3）。每代定型后就不再改。
· 支线/适配 = 给同一代车换轮胎、换屏幕、换发动机的试制车：把 APP 搬到鸿蒙板子（CarOH）、把控制程序塞进真车主控板（CarAgent）、把单车改成双车（CarDual）。车还是那代车，只是换了个跑法。
· 废弃分支 = 造了一半发现方向不对、推倒重来的样车（目录 V3，旧 TCP 多车方案）。
· 无关目录 = 隔壁部门放在同一个仓库里的空壳和别的课程材料（Application / culture / music）。

层V1V2V3

一句话：V1 改的是「怎么连」，V2 改的是「中间加一层云」，V3 改的是「一台变一队、加业务系统」。云侧物模型从 V2 到 V3 零改动，这也是路线图反复强调的硬约束。

8. 常见坑

① 目录 V3 ≠ 正式 V3。 E:\Harmony\Project\V3 是废弃的 TCP 多车底座；正式 V3 在 v3-fleet（后端）和 CarFleet（APP）。找代码时别进错门。
② 路线图里的 V1/V2 目录名在磁盘上找不到。 文档写的是 lab01-tcp-sim、iot-stage，实际落地对应 Car 和 IoTDA，文档命名与实物命名没对齐。
③ Car / CarOH 不是「纯 V1」。 两者都带 CloudClient.ets 和云端模式开关，同一份代码能切两种架构，别只看目录名判断版本。
④ 好几个 docs/项目分层验收方案.md 是从 Car 复制后没改的（CarDual、CarOH、CarFleet 里都还写着「适用范围：第一阶段 TCP 直连模拟」），不能拿它判断当前工程属于哪一代，要看 net/ 下的客户端类和端口。
⑤ CompleteProject 是 11-14 的快照。 之后新建的 culture 不在包里；包内的 04-previous-versions 收的是 8 个历史工程，01/02 才是当前 V3。

9. 自测三题（能答出来就算真的分清了）

① 如果老师问「你项目做了几个版本」，标准答案怎么说？

3 个正式版本：V1 TCP 直连单车、V2 华为云 IoTDA 云控、V3 巡检车队。再补一句：另有 4 条支线适配（双车 / OpenHarmony 移植 / 真车车端 / 课堂切片）和 1 个已废弃的旧 TCP 多车分支，不算正式版本。

② 想改「车队里第 3 台车的初始位置」，该进哪个目录？

v3-fleet/server/devices.json（正式 V3 的设备注册表）。不是 V3/car_server.py（废弃），也不是 IoTDA/car_mqtt_client_001.py（V2 写死单车）。

③ 看到 CarOH/docs/项目分层验收方案.md 写着「第一阶段」，能断定 CarOH 是 V1 吗？

不能。那份文档是从 Car 复制过来忘记改的。看 AppScope/app.json5（com.example.caroh）、build-profile.json5（OpenHarmony API 20）和 README-OpenHarmony构建说明.md 才知道它是「V1 业务代码换到 OpenHarmony 运行环境」的支线，且同时支持云端模式。
