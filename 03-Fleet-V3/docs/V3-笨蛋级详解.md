# V3 车队版 · 笨蛋级详解（零基础版）

> 这份文档假设你**什么都不懂**：不懂云端、不懂协议、不懂 APP 开发。
> 每一个概念都用生活里的东西打比方，每一步都讲"谁、对谁、干了什么、为什么"。
> 看完这份，你就知道这套系统里**任何一个动作**（点一下按钮、拖一下摇杆）到底发生了什么。

## 第 0 章 · 先用一个大比喻理解全局

把整个项目想象成一家**外卖公司**：

| 项目里的东西 | 比喻 |
|---|---|
| 小车（模拟器/真车） | **外卖骑手**。真正在路上跑的人 |
| 华为云 IoTDA | **公司总部**。骑手定期打电话报位置，总部有个记录板 |
| 设备影子 | 总部记录板上的**每骑手一栏白板**：写着他最后一次上报的位置、电量。骑手不在线也能看这栏（记录的是"最后一次"） |
| 业务后端 app.py | **客服中心**。所有顾客（网页、APP）都只打客服电话，不直接找总部。客服每 2 秒看一次总部记录板，抄到自己手边的本子上 |
| STATE_CACHE | 客服手边的**抄写本**——最新鲜的"全队位置表"，抄本比记录板最多旧 2 秒 |
| 网页监控大屏 | **顾客 A**，盯着屏幕看骑手在哪 |
| 管理后台 | **店长**，能招新骑手（注册）、开除骑手（删除）、罚站骑手（冻结） |
| APP | **顾客 B**，不光能看，还能给骑手下指令 |
| 摇杆命令 | 顾客告诉客服"让 1 号骑手往东走" → 客服转告总部 → 总部用对讲机喊给骑手 |
| 轨迹库 SQLite | **行车记录仪存档**，事后可以调出来看某骑手某天走过的路 |

**记住最重要的一条规矩：顾客永远不跟总部直接打交道，一切通过客服（后端）。** 这就是"STATE_CACHE 是全系统唯一状态源"的意思。

## 第 1 章 · 一台小车的"一生"（模拟器怎么工作）

打开 `device/car_mqtt_client.py --device car_001`，一台"车"就活了。它其实是一个 Python 程序，干四件事：

### 1.1 起床（初始化）
1. 读 `server/devices.json` 里属于自己那行：**我是谁**（云上的完整身份证号 `6ae6e3ef..._car_001`）、**门禁密码**（secret）、**出生点**（spawn，比如 (0,16)）、**我的私人电话分机**（http_port 8081）
2. 用这三样连接华为云总部的**对讲机专线**（MQTT，8883 端口，加密）
3. 连上那一刻，总部记录板上它的状态栏就变成"**在线（ONLINE）**"

> 为什么要"私人电话分机"（8081 端口）？因为每个模拟器进程都要开一个小网页服务（`/state`）方便本地调试。**如果这个端口被别人占了，它会拒绝启动**——这是防"两个我同时存在互相打架"（互踢）的保险。

### 1.2 走路（每秒 20 次的心跳计算）
程序内部有个小数学模型（CarSim），**每 1/20 秒**算一次：
- 我现在的速度方向是什么（车头朝向 theta、速度 speed）
- 按"距离 = 速度 × 时间"挪一点坐标（x 向东、y 向北）
- 电量按消耗速率掉一点点

这就是车为什么会"动"——全靠这个循环不停积分。你发的命令改变的只是这个模型的**输入参数**（方向和速度），模型自己负责把车"开"过去。

### 1.3 打电话报位置（上报）
每隔一段时间，把 `x, y, theta, speed, battery` 打包给总部：

| 什么时候报 | 隔多久 | 为什么 |
|---|---|---|
| 正在开（speed>0.01） | **5 秒**一次 | 路线图定死的规矩，为了省话费（云端配额） |
| 停着不动 | 60 秒一次 | 没变化，报个平安就行 |
| **刚收到命令** | **立刻报一次**（2 秒内最多一次） | 让所有人马上知道"我转向了！"——这是后来为了解决"命令后画面反应慢"加的 |

### 1.4 听对讲机（接命令）
程序一直竖着耳朵听总部的命令频道。听到 `move(vx, vy)` 就改行驶参数，听到 `stop` 就把速度归零。**收到就执行，马上生效**——车本身没有任何延迟，延迟都出在"消息怎么传"上（后面讲）。

> 关掉模拟器那个黑色命令行窗口 = 骑手把对讲机扔了 = 车下线。**黑窗只能最小化，不能关。**

## 第 2 章 · 总部（华为云 IoTDA）到底存了什么

总部干三件事，别的不管：

1. **对讲机接入**：谁拿对了身份证+密码，就让它上线
2. **记录板（设备影子）**：每台车一栏，存它**最后一次**上报的位置等数据。车离线了，这栏还留着（所以 APP 上能显示离线车的"最后位置"）
3. **命令信箱**：客服要给车下命令，不是直接喊，而是往信箱里投一张命令单（`move`/`stop`），总部负责用对讲机转给车，并给客服一个**命令编号**（command_id）作为回执

> 客服投完单子，总部只说"单子我收到了，会转达"，**不会**等骑手说"收到，已执行"才回复客服——这是我们这套系统里一个重要的简化（术语叫"拉模式"），后果是：客服只能说"命令已受理"，不能打包票说"车已执行"。好在车收到命令后会立刻上报位置，弥补了这个空缺。

## 第 3 章 · 客服中心（app.py，全系统的心脏）

Flask 程序，跑在 PC 的 **8000 端口**。它内部同时干着好几件事，一件件说：

### 3.1 后台刷新线程（poll_loop）——抄记录板
每 **2 秒**循环一轮：对每台注册过的车——
1. 问总部："它现在在线吗？"（ShowDevice）
2. 问总部："记录板那一栏写的什么？"（ShowDeviceShadow）
3. 抄到自己的**抄写本 STATE_CACHE**（内存里的一张表）

这就是为什么网页上的"在线/离线"最多滞后 2 秒。

### 3.2 对外服务（REST 接口）——接顾客电话
顾客（网页/APP）用 HTTP 请求打电话来，常用的几路电话：

| 电话号码（接口） | 说人话版 |
|---|---|
| GET `/fleet/status` | "报一下全队现在的位置！" → 客服照着抄写本念一遍 |
| GET `/track?device_id=...&from=...&to=...` | "把 1 号车昨天下午的路线调出来" → 去档案库查 |
| POST `/command` | "让 1 号车转向东边，速度 70！" → 客服转单给总部 |
| WebSocket `/ws` | **不是顾客打电话，是客服主动一直念**：只要有顾客把耳朵贴上来（连接），客服就持续把抄写本内容念给他听。命令一受理还会**插播**（详见第 5 章） |

### 3.3 档案室（track_store.py + SQLite）
- 抄记录板时，如果某车的位置**和上次比变了**，就往档案库添一行（时间、地点、速度、电量）
- **没变化不添**（车停着，位置一样，存一万行没意义）
- **乐观回显的"猜的值"绝不入库**（档案必须真实，见第 5 章）
- 档案自动清理：超过 7 天的删，总量超 2 万条删老的

### 3.4 店长办公室（/admin/* 接口）——唯一能"改世界"的地方
其他接口只读，admin 接口能**改变系统本身**：

| 操作 | 实际发生的事 |
|---|---|
| 注册新车 | ①先查总部有没有同名的残留（有就先删掉，防"已存在"报错）→ ②让总部建档案 → ③devices.json 加一行（自动分配颜色、出生点、私人分机号）→ ④把一次性密码告诉店长 |
| 删除车 | ①先把它正在跑的模拟器进程杀掉 → ②总部删档案 → ③devices.json 删行。至少留一台车，全删光会拒绝 |
| 冻结/解冻 | 在 devices.json 打个标记。冻结后所有 `/command` 对这车直接拒绝（403） |
| **上线** | 客服自己动手在 PC 上**启动一个模拟器进程**（就是执行 `python car_mqtt_client.py --device car_00N`）。启动前会先扫一遍：有没有僵死的旧进程占着分机号？有就先清掉 |
| **下线** | 按命令行特征（进程参数里带 `car_mqtt_client.py --device car_00N`）**找到本机所有相关进程，全部杀掉**——不管是谁、什么时候启动的。这就修掉了"后端重启后不认识旧进程、下线按钮失灵"的 bug |
| 云端对账 | 把总部的档案名单和本地 devices.json 逐个对比，标出"两边一致 / 云端残留 / 本地多出"。残留可以一键清 |

> **为什么 APP 能让车上"线"？** 因为"上线"的本质是"PC 上跑一个程序"，而模拟器就跑在这台 PC 上。APP 发请求 → 客服替它启动进程 → 进程连上总部 → 车在线。真车时代这一步就不需要了（真车自己会开机上线）。

### 3.5 登录（admin 怎么验证身份）
- `POST /admin/login`，账号 admin / admin123（写死在代码里的演示账号）
- 登录成功发一个**临时通行证 token**（随机字符串）。之后每个 admin 请求都要带上，放在请求头 `X-Auth-Token: xxx` 里
- token 存内存里 → **后端一重启，所有通行证作废，要重新登录**（这不是 bug，是设计）

## 第 4 章 · 顾客们（网页三件套 + APP）

### 4.1 监控大屏 monitor.html —— 看车的
- 打开 `/monitor/view`，通过 WebSocket 把耳朵贴在客服那里，持续收全队位置
- 画布上每台车画成一个**小车形状**（和 APP 里一模一样）：颜色区分、车头指向真实朝向、拖着最近的轨迹尾巴、地图自动缩放
- 点选某台车 → 摇杆就能控制它
- 摇杆规则：**按下不动作，拖到哪车往哪走（保持），拖回中心=停车，双击=急停**

### 4.2 管理后台 admin.html —— 店长用的
- 登录 → 三个页签：总览 / 设备管理 / 命令历史
- 设备管理是**卡片式两行布局**（手机屏幕窄放得下）：第一行名字+状态，第二行三个按钮（上线/下线、冻结/解冻、删除）
- 还有一个"云端对账"面板
- 所有确认框和报错提示都是**页面自己画的弹窗**——因为 APP 内嵌的浏览器组件**不显示**浏览器原生的 confirm/alert 弹窗（原生的会被静默吞掉，按钮看起来"没反应"，这是个真实踩过的坑）

### 4.3 轨迹回放 track_demo.html —— 查档案的
- 选车、选时间窗（最近 1/6/24 小时等）→ 画布画出走过的路线
- 数据来自 GET /track，纯历史档案

### 4.4 APP（CarFleet 工程，鸿蒙 ArkTS）
四个页面（视图）：
1. **车队页**：顶部摘要卡 + 每台车一张卡片，点卡片选中
2. **操控页**：300vp 实时地图（画全部车，点选切换）+ 摇杆 + 状态三格（速度/电量/位置）
3. **轨迹回放页**：Canvas 画历史轨迹 + 4 档时间窗 + 点数/里程统计
4. **管理后台页**：Web 组件直接内嵌电脑版的 `/admin/view` 网页（所以后台功能在手机上跟电脑完全一样，后台改了 APP 自动跟着变，不用重新构建 APP）

APP 的网络层（FleetClient.ets）只有四个动作：
- 每 **800ms** 轮询一次 `/fleet/status`（相当于每 0.8 秒问一次客服）
- `bind()`：换一台车控制（只是本地换个选中目标，不用重新连接）
- `sendCommand()`：发控制命令
- `fetchTrack()`：调轨迹

## 第 5 章 · 最精彩的部分：你拖一下摇杆，到底发生了什么？（完整流水账）

假设你在大屏上选中 1 号车，把摇杆拖向右边（向东，速度 80%）。按时间顺序：

```
T+0.000s  你松手定格
          网页 → 客服：POST /command {device_id: car_001, cmd: MOVE, angle: 90, speed: 80}

T+0.0xxs  客服检查：这车注册了吗？冻结了吗？参数合法吗？
          （换算：angle=90 向东 → vx = sin(90°)×0.8 = 0.8 米/秒, vy = cos(90°)×0.8 = 0）
          客服 → 总部：投命令单 move(0.8, 0)
          总部：单子收到，编号 CMD-12345

T+0.03xs  【快通道开始】客服不等车执行，直接在抄写本上"预填"：
          1 号车朝向=90°（东）、速度=80 —— 这叫"乐观回显"（乐观=先斩后奏）
          同时按广播铃：立刻给所有连着的网页推一帧最新状态
          （命令受理到画面反应，实测约 0.33 秒）

T+0.33s   网页收到这一帧：咦，1 号车朝向变了！
          网页的"航位推算"开始干活（见 5.1）
          —— 你看到的画面里，车已经开始转向了

T+0.3~1s  【慢通道开始】总部把命令单用对讲机喊给车
          车收到 move(0.8, 0) → CarSim 模型立刻改参数 → 车真的开始向东开
          车 → 总部：立刻补报一次位置（"我已经朝东了！"）

T+1~2s    客服抄记录板时发现：1 号车朝向=90、速度=80 —— 和预填的一致！
          → 确认无误，清除"待确认"标记。真实数据接管，一切继续

（如果车离线/命令失败：总部会报错，客服收到错误返回给网页；
  如果 4 秒内真实数据一直没来，预填的值会被过期机制放行/修正，不会卡死）
```

### 5.1 网页端的"航位推算"是什么？（流畅度的秘密）

**问题**：车 5 秒才报一次位置。如果画面只画"收到的坐标"，车就是每 5 秒瞬移一格，一卡一卡的。

**解决**：网页学会"脑补"。两次观测之间，按车的**朝向和速度自己推算**它现在该在哪：
- 每帧（1/60 秒）把车往前画一点点：距离 = 速度 × 时间，方向 = 朝向
- 收到**真实位置**（x/y 变了）→ 用新位置修正自己推算的轨迹（起点对齐）
- 收到**命令回显**（只有朝向/速度变了，位置没变）→ **不重置位置**，把旧位置沿旧方向推进到当前时刻，再换新方向——因为真车就是这样运动的（走到一半才转向，走出的路是一条折线）
- 8 秒没新消息 → 认为"消息可能堵了"，3 秒内慢慢减速滑停（防止车影一直漂走）

这样画出来的运动是 60 帧丝滑连续的，且和车真实走过的路径几乎重合。

> 想对比"不开脑补"的诚实版？网址后加 `?plain=1`，就回到"5 秒一跳"的纯观测模式。

### 5.2 延迟一览表（现在每段还剩多少）

| 环节 | 延迟 | 能不能更快 |
|---|---|---|
| 你动手 → 画面车转向 | **≈0.33 秒** | 已经是极限（乐观回显） |
| 你的命令 → 车真的转向 | ≈0.3~1 秒 | 云端下单+对讲机，物理极限 |
| 车转向 → 画面确认无误差 | ≤2 秒 | 等真实上报校准，5 秒上报节奏是配额硬约束 |
| 车停下 → 画面看到停 | ≈0.36 秒 | 同上（乐观回显） |

## 第 7 章 · 常见问题（笨蛋版 FAQ）

**Q：为什么有的车显示在线，有的离线？**
A：在线 = 它的模拟器进程正在这台电脑上跑着且连上了总部。离线 = 进程没跑（被你点了下线/黑窗被关了/还没启动）。想让谁上线 → 管理后台点"上线"。

**Q：点了删除没反应？**
A：旧版 bug，APP 内嵌浏览器不弹原生确认框。已修：现在是页面自绘弹窗，点"确认删除"才真删。如果还遇到"没反应"，先退出管理后台页签重新进（刷新网页）。

**Q：APP 里的改动怎么生效？**
A：ArkTS 代码（Index.ets/FleetClient.ets）改动 → DevEco 重新构建运行。网页（web/*.html）改动 → 刷新页面/重进页签即可，后端是实时读文件提供的。

**Q：后端重启后要做什么？**
A：重新登录管理后台（通行证作废）。模拟器进程不受影响（它们是独立进程）。
