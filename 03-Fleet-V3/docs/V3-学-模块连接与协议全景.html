1

一句话结论

先背这一句
项目是「三层两云」：前端（APP／网页）只跟 业务后端 8000 说话；业务后端用 HTTPS + 华为云 SDK 跟 IoTDA 云端说话；小车模拟器用 MQTT over TLS（8883） 跟 IoTDA 说话。中间没有任何一条线是"APP 直连小车"。 再加一句：为了画面流畅，模拟阶段额外开了一条不出局域网的紫色近路——后端每 0.1 秒直接读模拟器进程内存里的位置，这只是教学期的"作弊通道"，不产生任何云端消息，接真车时会关掉。

① 控制下行

你点摇杆 → HTTP 短连接 → 后端换算 → HTTPS 下发命令 → MQTT 送到车。橙色线。

② 状态上行

车定时上报 → 设备影子 → 后端每 2s 拉一次 → 存缓存／轨迹库。青色线。

③ 本地旁路

后端 10Hz 直读 /state，只为把画面做丝滑。紫色虚线，仅模拟阶段。

④ 展示回路

WebSocket 推给大屏；APP 用 800ms 轮询；轨迹页读 SQLite。蓝色线。

2

生活比喻：把项目想成一家「外卖公司」

不用记术语

先把名词换成生活里的东西，后面看协议就不会晕。

项目里的东西相当于它在干嘛（白话）
APP / 监控大屏 / 管理后台顾客手机上的点餐页只负责"显示"和"下单"。它不知道厨房在哪、也不认识骑手，只认识一个电话号码：后端 8000。
业务后端 Flask（:8000）店里的接单调度台接单、查身份、把"往东北方向 60% 速度"翻译成云平台听得懂的 vx/vy、记台账、给顾客播报进度。全项目唯一的中枢。
华为云 IoTDA平台调度中心 + 留言板它不直接开车，只做两件事：把命令转交给车；把车最后一次汇报的位置写在设备影子（留言板）上，谁想看自己来读。
设备影子 Shadow留言板 / 快递柜车不用一直在线等别人问；它把最新状态"贴"上去就走。后端每隔 2 秒来抄一次。所以你看到的位置天然是几秒前的快照。
模拟器 car_mqtt_client.py骑手 + 车一个黑窗 = 一台车。内部每秒 20 次算自己在哪（积分），按纪律每 5 秒（行驶）／60 秒（静止）往平台上报一次。
SQLite fleet.db店里的行车账本只有"真实上报且状态变了"才记一笔，供轨迹回放翻旧账。不是网络协议，就是本机一个文件。
WebSocket /ws店里的实时播报喇叭后端状态一变就主动喊一嗓子，网页不用每秒敲门问。APP 没接这个喇叭，所以它是自己每 800ms 敲门问一次。
本地高速旁路 /state隔着玻璃直接看骑手不走平台、不打电话，直接看一眼车此刻在哪。模拟阶段用来让画面丝滑，接真车就没有这扇玻璃了。

为什么中间非要夹一个"后端"？

因为 华为云的账号密钥（AK/SK）绝对不能放进 APP 或网页里——前端代码谁都能看到。所以密钥只放在 PC 上的 server/cloud_config.json，由后端一个人拿着去调云端 API；前端只跟自家后端说"我要控制 3 号车"。这也是全项目最重要的一条安全边界。

四种"连接"别混成一谈

初学者最容易卡在这里：以为"连接"都是同一种东西。实际有四类，性质完全不同：

① 网络协议

HTTP / WebSocket / MQTT / TLS。规定"数据怎么打包、怎么传"。

② 应用接口

/command、/fleet/status、设备影子、topic。规定"传什么内容"。

③ 进程内调用

后端函数互相调用、sqlite3 读写文件。压根不出网卡。

④ 操作系统操作

后台"上线/下线"用 subprocess 启停 Python 进程、taskkill 杀进程。也不是网络协议。

统一的数据格式：所有 HTTP 接口都用同一个"信封"

成功 → {"ok": true,  ...数据}
失败 → {"ok": false, "error": "错误说明"}   （HTTP 状态码 400 / 403 / 502）
WebSocket 帧 → {"type":"fleet_state","ts":1699..., "cars":[{device_id,name,color,online,x,y,heading,speed,battery,time}, ...]}

这就是《V3-接口协议设计.md》说的"响应包络"。前端只判断 ok，不用为每个接口写一套解析。

为什么"点完不会立刻动"？—— 一条时间轴看懂延迟

纯云端链路最慢要 5s 上报 + 2s 轮询才在大屏体现；本地旁路把这段绕过去，所以网页看起来是丝滑的。但轨迹库只认真实影子，不会被旁路"污染"。

三条回路是互相独立的，别搅在一起

控制回路（橙）：短连接、一次性、只管"把意图送到"。/command 返回 200 只代表云平台受理了，不代表车已经跑完。

状态回路（青）：长连接 + 定时上报 + 后端定时拉。它是"快照"，天生有秒级延迟，配额约束 5s/60s 不能随便调快。

展示回路（蓝 + 紫）：只影响"你眼睛看到的"，不改变车的真实运动。APP 走蓝色 800ms 轮询，网页走蓝色 WS 推帧，本地旁路是紫色加速补丁。

判断口诀：问"数据有没有真的进云"看青线；问"车有没有收到命令"看橙线；问"画面卡不卡"看蓝线/紫线。

协议速查卡（考试/答辩用这一张就够）

HTTP / 1.1 · 短连接

APP 轮询、后台接口、本地 /state。一次请求一次回答，简单、无状态、好调试（curl 就能测）。

WebSocket · 长连接

网页 /ws。由 HTTP 升级而来，连上后服务端可主动推帧，省掉反复敲门；断线要自己重连（项目做了指数退避）。

MQTT over TLS · 长连接

设备↔云。发布/订阅 topic + QoS1 + TLS 8883，专为弱网小设备设计；身份用 HMAC-SHA256 三元组。

HTTPS REST + SDK 签名

后端↔云应用侧。AK/SK 由 SDK 自动签名，走 443；查设备/影子、下发命令、注册删除设备。

设备影子（不是协议，是数据模型）

云端保存的"最后一次上报的 JSON"。后端拉模式的关键：车不在线也能读到历史状态。

SQLite / 进程调用

本机文件 + 函数互调，不出网卡。轨迹库和状态缓存属于这一类，别算进"网络协议"。

常见坑（都是这个项目真实踩过的）

对照排错
现象原因记住这一条 / 代码位置
查在线状态查出网关等无关设备ListDevices 的 device_id 过滤参数在标准版不生效单台状态一律用 ShowDevice，且 resp.status 是平铺字段。app.py:135
命令 400 / 设备不响应把 service_id 写错了：命令是 car_control，属性上报是 car_status两个服务别混；命令名 move/stop 挂在 car_control 下。app.py:59,163
SDK 按官方文档写却报类不存在V5 SDK 命令体类名是 DeviceCommandRequest；影子响应是 shadow[].reported.properties（值可能是 Decimal）以实际 SDK 为准，别照抄旧文档模板。app.py:45,143
小车画面一顿一顿云端链路被 5s/60s 上报 + 2s 轮询限制，这是配额硬约束不要偷偷调快上报；用命令事件补报（≤2s）和本地旁路（10Hz）改善观感。car_mqtt_client.py:43、app.py:73
接真车后位置乱跳本地旁路还在读根本不存在的 127.0.0.1:808N真车阶段设 V3_LOCAL_FAST=0，回退纯云端链路；离线端口 1s 内跳过。
/command 返回 200，车却没动200 只表示"云平台已受理"，不是"设备执行完回执"；设备可能掉线协议原设计要等 20s 同步回执，拉模式做不到；先去后台点"上线"再看 MQTT 黑窗。app.py:630~646
8000 端口请求被"旧后端"抢走Windows 上旧 Python 进程没杀干净，新旧进程同时监听重启前查端口占用并结束旧 PID；每台模拟器 808N 也唯一，端口串了会被 sid != did 拒绝。app.py:368~370
APP 里点"删除"没反应鸿蒙 Web 组件会吞掉原生 confirm/alert后台页面改成自绘 #modalMask 弹窗，浏览器和 APP 内嵌都能用。web/admin.html
APP 连不上、页面空白APP 里写 127.0.0.1 指的是手机自己，不是 PC填 PC 的局域网 IP，且手机与 PC 同网段；后端监听 0.0.0.0:8000 才对外可见。
MQTT 一连就被拒（Bad user name or password）设备密钥错，或三元组用的 UTC 小时时间戳与平台不一致三元组 = clientId={did}_0_0_{UTC小时} / username={did} / password=HMAC-SHA256(密钥, 时间戳)；控制台重置密钥可解。car_mqtt_client.py:140
关掉一个黑窗，某台车立刻离线黑窗就是模拟器进程本体，关了 MQTT 长连接就断最小化可以、关闭不行；在线状态由 ShowDevice 判定，本地 /state 也会失效。
轨迹回放里出现"假点"乐观回显或本地旁路的数据被写进了轨迹库只认真实影子观测、且状态有变化才插行。app.py:291~303
