先建立学习方法

约 3 分钟读完

「总体把控、面、线、点」本质上是四种观察距离：先站在山顶看全貌，再摊开地图看分区，然后沿着一条路走一遍，最后蹲下来研究一块石头。不要一上来就钻代码，那样只见树木不见森林。

LEVEL 1
总体把控
这系统到底在干什么？由哪几大块组成？一句话能不能给别人讲明白？
LEVEL 2
面
摊开几张地图：分层图、网络图、文件地图、数据地图。知道每块地盘归谁。
LEVEL 3
线
挑一条完整流程从头走到尾：控车、上线、状态上报、轨迹、管理。接口都长在线上。
LEVEL 4
点
钻进一个文件、一个函数、一个字段：它为什么这么写、改了会影响谁。

为什么这个顺序有效

  • 先有框架，细节才有地方挂：知道"后端是唯一枢纽"，再看到 STATE_CACHE 就不陌生。
  • 线比面容易记：一条"摇杆 → 车动"的流水账，比一张静态架构图更能建立因果感。
  • 点要带着问题钻：先问"为什么车会卡"，再看航位推算代码，才看得懂。

每层的过关标准

  • 总体：能用 30 秒给外行讲清楚这项目。
  • 面：能画出五个端和四条层间连线。
  • 线：能不看资料复述"拖一下摇杆之后发生了什么"。
  • 点：能指出某个功能该改哪个文件、改完影响哪些页面。

30 秒项目全景（先记住这一小段就够开始）

有 多台模拟小车，每台是一个独立进程，通过 MQTT 连到华为云 IoTDA，定期把自己位置写进"设备影子"。PC 上跑一个 业务后端（app.py，端口 8000），它每 2 秒去云端抄一次影子，抄进自己的缓存，所有页面和 APP 都只问这个后端、绝不直连云端。于是网页大屏能看实时地图和摇杆控车，管理后台能注册/上下线/冻结设备，轨迹回放页能查历史路径，鸿蒙 APP 能做同样的事。

一句话比喻（后面反复用）：小车 = 骑手，华为云 = 总部记录板，后端 = 客服中心，缓存 = 客服手边的抄写本，网页和 APP = 打电话来问的顾客。铁律：顾客永远不直接找总部。

按《V3-开发路线图》，①~⑥ 步（多车底座 / 后端 / 轨迹 / 大屏 / 后台 / APP）已实现并通过测试；⑦AI 增强、⑧真车接入是路线图预留的后续方向，当前版本尚未实施。

总体把控

目标：能讲给别人听

这一层只回答四个问题，不碰任何代码细节。

四个问题

  • 解决什么问题：把"一台车"扩成"一支车队"，并且让网页 / APP / 后台三种角色共享同一份状态。
  • 分成哪几块：模拟小车端、华为云 IoTDA、业务后端、网页客户端、鸿蒙 APP。
  • 谁说了算：STATE_CACHE（后端缓存）是全系统唯一状态源。
  • 最关键的约束：客户端不直连云端；小车↔云端的 MQTT 报文格式是"合同"，将来换真车上面三层不用改。

三个最容易搞混的概念

  • 设备影子 ≠ 实时位置：影子只是"最后一次上报"的快照，可能几秒前。
  • 命令受理 ≠ 命令执行：云端返回 command_id 只代表"信已投递"。
  • 轨迹回放不是一个独立服务：它没有自己的进程和端口，只是调用 GET /track 的一个视图。

线：走通五条完整流程

目标：理解模块怎么协作

「线」是学习收益最高的一层。接口不是背出来的，是在一条流程里自然出现的——每一步"谁把什么交给谁"，就是接口。

线 1 · 控车线（最核心，务必先走通）

摇杆拖动 → 前端 POST /command（MOVE angle+speed）→ 后端换算 vx=sin(a)·r, vy=cos(a)·r → 云端 CreateCommand 下发 → 快通道：受理成功即"乐观回显"，把预期朝向写进缓存并立即推 WebSocket（约 0.3 秒页面就转向）；慢通道：MQTT 到模拟器 → on_message 立即执行 → 命令事件补报 → 影子更新 → 后端 2 秒轮询校准（约 1~2 秒）。

涉及文件：web/monitor.html（摇杆 + 分段航位推算）、server/app.py（/command、回显守卫）、device/car_mqtt_client.py（命令解析 + 事件补报）。这条线解释了项目里几乎所有"手感"相关的设计。

线 2 · 上线线（APP 里点一下，车怎么就在线了）

管理后台"上线"按钮 → POST /admin/devices/{id}/start → 后端先清理僵进程，再用 subprocess 拉起 car_mqtt_client.py --device car_00N（PC 上弹出黑窗）→ 模拟器读注册表拿身份/密钥/出生点 → MQTT 连上 IoTDA → 云端状态变 ONLINE → 后端轮询 ShowDevice 发现 → 全端显示在线。"下线"反过来按命令行特征终止进程。

关键认知：在线状态由设备自己的 MQTT 连接决定，后端无法凭空改；黑窗关掉 = 车下线。

线 3 · 状态上行线（位置怎么传到屏幕）

CarSim 以 20Hz 积分出真实位置 → 本地 /state 调试口（后端 10Hz 并发直读，零云端消息，模拟阶段专用的高速旁路）／同时按 5s 行驶、60s 静止、命令后 ≤2s 事件补报走 MQTT 写影子 → 后端 poll_loop 每 2 秒拉影子 → 合并进 STATE_CACHE → 分发给大屏 WebSocket、APP 轮询、轨迹库。

配额是这条路被设计得"绕"的根本原因：IoTDA 免费单元约 1 万条/日，5 台车不能秒报。真车接入时用环境变量 V3_LOCAL_FAST=0 关掉旁路。

线 4 · 轨迹线（历史怎么被保存和回放）

后端每次拿到真实影子观测（不是回显、不是旁路值）→ 与上一帧比较，变化才插一行 → SQLite WAL 表 track_points（7 天过期 + 2 万条上限）→ GET /track?device_id=&minutes= → 轨迹回放页 Canvas 画线 / APP 车辆详情页 Canvas 画线。

关键设计：预测值绝不入库，保证历史数据保真。

线 5 · 管理线（唯一能"改世界"的部分）

登录拿 X-Auth-Token → 注册（云端 AddDevice + 写 devices.json + 返回一次性密钥）／冻结（命令直接 403）／删除（云端 DeleteDevice + 移注册表 + 停模拟器）／云端对账（ListDevices 与本地比对，找残留）／命令历史审计（commands.log）。

为什么 APP 里"删除"曾没反应：HarmonyOS Web 组件吞掉原生 confirm()，所以弹窗改成页面自绘——这是"点"层面很典型的一课。

点：钻进具体文件与代码

目标：能读懂、能改、知道影响面

到了这一层，建议一次只学一个点。下面按文件分组，每一条都是可以直接拿来提问的题目。

device/car_mqtt_client.py · 小车本体
  • CarSim 为什么是 20Hz 积分，位置怎么由 speed + heading 算出来
  • 三档上报节奏（5s / 60s / 命令后 ≤2s 事件补报）是怎么实现的，限流为什么必要
  • MQTT 连接三要素（clientId / 用户名 / 密码）与密钥从哪来
  • on_message 怎么解析 move/stop，为什么 service_id 是 car_control 而属性是 car_status
  • 本地 /state 调试口与 8081~8085 端口，"端口被占用即退出"防呆
server/app.py · 后端枢纽
  • DEVICES / REGISTRY 怎么从 devices.json 加载，node_id 为什么要按第一个下划线切
  • STATE_CACHE 的数据结构与锁，为什么所有接口都读它
  • poll_loop 与 local_fast_loop 两个线程的分工、合并顺序、_merge_local_entry
  • 乐观回显 _echo_command_state 与 ECHO_PENDING 守卫（旧影子为什么不能覆盖回显）
  • /command 六种 cmd 与 MOVE 的矢量换算、"已受理不等于已执行"
  • WebSocket /ws 的事件驱动 + 0.5s 兜底广播，fleet_state 帧字段
  • 管理接口全套：token 鉴权、注册、冻结、注销、对账、启停进程
server/track_store.py 与 devices.json · 存储与配置
  • SQLite WAL 表结构、为什么"变化才插行"、7 天 / 2 万条治理
  • devices.json 每个字段（完整云 ID、secret、spawn、color、http_port、frozen）谁在读
  • cloud_config.json 的 AK/SK/project_id/endpoint 用在哪些 SDK 调用上
  • commands.log 审计格式，排查问题时的第一现场
web/monitor.html · 实时监控大屏
  • fitCanvas 画布自适应、drawCar 与 CAR_SCALE 车形缩放、SHOW_TRAIL 拖尾开关
  • applyObs / estPos 分段航位推算：真实修复与命令回显为什么要区别对待
  • ?plain=1 纯观测模式、?trail=1 拖尾模式的用途
  • 摇杆语义：松手保持、拖回中心停、双击急停；为什么按下时不发命令
web/admin.html 与 web/track_demo.html · 后台与回放
  • 卡片式两行布局为何适配手机；自绘确认弹窗与 Web 组件吞 confirm() 的坑
  • 上线/下线按钮随状态切换文案；刷新等待时间为什么是 4~4.5 秒
  • 轨迹回放页的时间窗、车辆筛选、点数与里程统计、Canvas 自适应
CarFleet（鸿蒙 APP 工程）
  • net/FleetClient.ets 四个方法：startPolling(800ms)、bind、sendCommand、fetchTrack
  • pages/Index.ets 四视图（车队 / 操控 / 轨迹详情 / 内嵌后台）如何切换
  • carShape 车形缩放、carNo 解析（为什么曾全部显示"6号"）
  • Preferences 记住选中的车；Web 组件内嵌 /admin/view 需要哪两个开关
  • APP 与后端只走 HTTP + JSON（没有 WebSocket、没有 MQTT），为什么这样选
华为云 IoTDA · 云端与 SDK
  • 三大能力：MQTT 接入、设备影子、命令队列；影子响应结构 response.shadow[].reported.properties
  • 六个 SDK 调用：ShowDevice / ShowDeviceShadow / CreateCommand / AddDevice / DeleteDevice / ListDevices
  • 踩坑：ListDevices 过滤参数不生效、limit 上限 50、命令体类名是 DeviceCommandRequest
  • 物模型报文：上报 topic、car_status 属性、car_control 命令体
测试与辅助脚本
  • server/test_api.py 50 项自测各在验证什么；device/verify_step1.py 第①步验收
  • server/drive_cars.py 造轨迹数据的原理与结束自动刹停
  • 启动脚本 start_car_00N.bat / start_all_cars.bat，以及"后端先起、车后上"的顺序

约定固化

你可以用这几种问法

  • 按层点菜：「给我讲『面』里的网络拓扑」「讲『线』里的控车流程」
  • 按文件点菜：「逐段讲 app.py 的轮询线程」
  • 按疑问点菜：「为什么要乐观回显，不做会怎样」
  • 按对比点菜：「V2 单车和 V3 多车的数据链路差在哪」
  • 按踩坑点菜：「把项目里所有 bug 和修法整理成一份」
  • 按考核点菜：「出 10 道题考我，附答案」

我会交付什么

每个知识点一份独立 HTML，固定结构：

  • 一句话结论（先给答案，不绕弯）
  • 生活比喻 + 在四层架构里的位置
  • 涉及的文件、接口、数据字段
  • 逐步拆解（配 SVG 图 / 时序图 / 表格）
  • 与前后知识点的连接（这条"线"通向哪里）
  • 常见坑 + 自测小问题

全部放 docs/，双击即可看，不依赖后端运行。

一条最省力的起步建议

先别贪多。按这个顺序连问三次，整套骨架就立起来了：

① 「用最白话讲一遍项目在干什么」 → ② 「把五个端和它们之间的连接画成图」 → ③ 「把拖一下摇杆的全过程做成时序图」。这三份 HTML 就是你的"总体 → 面 → 线"三块基石，之后再随便点哪个"点"都不会迷路。
