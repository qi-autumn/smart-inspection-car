# V3 车队版 · 分层架构与接口详解

> 阅读顺序建议：先看 §0 分层总则 → 再逐层看 L1→L4 → 最后看 §6 三个跨层场景把各层串起来。
> 本文与《V3-项目架构详解.md》（接口参数版）、《V3-笨蛋级详解.md》（比喻版）互补。

---

## 0. 分层总则（为什么这样分）

```
L4 客户端层   网页×3 + APP          —— "看和操作"
L3 业务后端层 app.py + track_store  —— "唯一的数据枢纽"
L2 云平台层   华为云 IoTDA          —— "哑巴信箱"（只存只转，不懂数据含义）
L1 设备层     car_mqtt_client ×N    —— "真正会动的东西"
```

**三条铁律（所有模块设计都遵守）：**

1. **依赖只允许相邻层**：L4 只能调 L3；L3 只能调 L2（SDK）和管 L1（进程）；L1 只和 L2 说话。任何跨层直连（如网页直连 IoTDA）都是违规。
2. **状态只有一个源头**：L3 的 STATE_CACHE。L4 永远从缓存读，不读 L2 影子本身；L2 影子只是缓存的"上游进货渠道"。
3. **换层不改协议**：L1↔L2 的 MQTT 协议（物模型）是合同，将来真车替换模拟器，L2/L3/L4 全部零改动。

## 1. L1 设备模拟层 —— "每台车一个进程"

### 模块与职责

| 模块（文件内） | 职责 |
|---|---|
| `car_mqtt_client.py` 主程序 | 参数化入口 `--device car_00N`：从 devices.json 读身份/密钥/出生点/调试端口，连云、上报、听命令 |
| `CarSim` 运动模型 | 20Hz 积分：`x += v·sin(θ)·dt, y += v·cos(θ)·dt`，电量衰减。命令改的只是它的输入（v、θ） |
| 上报循环 | 行驶 5s / 静止 60s / 命令后≤2s 事件补报（限流） |
| 本地调试 HTTP `/state` | 8081~8085 端口，吐出进程内存里的 20Hz 实时状态（仅调试用，**不参与正式数据链路**） |

### 对下（L2）的接口 —— 全部走 MQTT

| 方向 | Topic | 内容 |
|---|---|---|
| 上行 | `$oc/devices/{id}/sys/properties/report` | car_status 服务：`{x, y, theta, speed, battery}` |
| 上行（回执） | `$oc/devices/{id}/sys/commands/request_id={rid}` | 命令回执（当前简化实现只回状态，完整回执是第⑧步升级项） |
| 下行（订阅） | `$oc/devices/{id}/sys/commands/#` | car_control 服务：`move(vx, vy)` / `stop` |

**消费的配置**：devices.json 中自己那一行（device_id 全名、secret、spawn、http_port）。
**对外提供**：一个 MQTT 连接 + 属性上报流 + 命令执行能力。**这就是"车"的全部定义**——真车只要做到这三点即可顶替。

### 与 L3 的一条特殊连接（非协议）

L3 的管理模块可以用 subprocess **直接启动/终止本进程**（上线/下线按钮）。这不是协议，是运维通道：L3 按命令行特征（`car_mqtt_client.py --device car_XXX`）识别进程，启动用 CREATE_NEW_CONSOLE，终止用 taskkill 全匹配实例。

## 2. L2 云平台层 —— 华为云 IoTDA（哑巴信箱）

### 三个服务模块

| 模块 | 接口 | 说明 |
|---|---|---|
| MQTT 接入 | 8883/TLS，设备三元组认证 | 只管"连接在不在"，不管数据含义 |
| 设备影子 | SDK：`ShowDeviceShadow` | 每设备存**最后一次** car_status 上报快照；车离线也可读 |
| 命令队列 | SDK：`CreateCommand` | 投递 car_control 命令给在线设备，返回 command_id（受理回执，非执行回执） |

### 两面的接口

**对下（L1）**：MQTT 协议（见 §1 表格）。
**对上（L3）**：应用侧 HTTPS API（V5 SDK 封装，AK/SK 鉴权）：

| SDK 方法 | 用途 | 已踩坑 |
|---|---|---|
| ShowDevice | 查单台在线状态 | ListDevices 的过滤参数不生效 → 必须逐台查；resp.status 平铺 |
| ShowDeviceShadow | 读影子 | 属性在 `resp.shadow[].reported.properties`，值是 Decimal |
| CreateCommand | 下发 move/stop | 命令体类是 DeviceCommandRequest（非文档的 CommandBody） |
| AddDevice / DeleteDevice | 注册/注销 | 注册前先 DeleteDevice 清残留，否则报"已存在" |
| ListDevices | 云端对账 | limit 上限 50（传 100 报 400） |

**L2 的设计本质**：它不解析 x/y/theta 是什么意思，不存历史，不做业务判断。所有"智能"都在 L3。这是"哑巴信箱"的含义——好处是换云厂商时 L3 只改 SDK 封装一个文件。

## 3. L3 业务后端层 —— app.py :8000（系统的心脏）

### 内部七个模块及相互关系

```
                    ┌────────────────────────────┐
 poll_loop ──写──▶ STATE_CACHE ◀──读── REST/WS ──▶ L4
 (2s轮询SDK)        (CACHE_LOCK)     (22端点+/ws)
     │写             ▲    │
     │            乐观回显 │写
     ▼               │    ▼
 ECHO_PENDING 守卫 ──┘  track_store ──▶ SQLite
                          (只入真实观测)
 admin 模块 ──▶ SDK(AddDevice/DeleteDevice/ShowDevice/ListDevices)
            └──▶ subprocess(拉起/杀模拟器进程, 管 L1)
```

| 模块 | 职责 | 与谁交互 |
|---|---|---|
| **poll_loop 轮询线程** | 每 2s 对每台车调 ShowDevice（在线）+ ShowDeviceShadow（属性）→ 写缓存；变化时写轨迹库 | ↓L2 SDK，→缓存/轨迹库 |
| **STATE_CACHE** | 内存字典，全系统唯一状态源，CACHE_LOCK 保护 | 所有模块围绕它读写 |
| **ECHO_PENDING 守卫** | 命令受理后 4s 内，**旧影子不得覆盖乐观回显值**；真实回报（值变化）即清除；超时放行 | poll_loop 与回显之间 |
| **REST API（22 端点）** | 查询/控制/轨迹/管理（见 §3.1） | ←L4，→缓存 |
| **WebSocket /ws** | fleet_state 帧：事件驱动（WS_DIRTY）+0.5s 兜底 | ←L4，→缓存 |
| **乐观回显** | /command 受理成功即把预期 heading/speed 写缓存并立即推帧（命令→画面 ≈0.33s） | /command →缓存 →/ws |
| **track_store** | SQLite WAL：真实观测且变化才插行；7 天过期+2 万条上限；**回显预测值绝不入库** | poll_loop → SQLite |
| **admin 模块** | 注册/删除（SDK）/冻结（注册表标记）/上线·下线（subprocess 管 L1）/对账（ListDevices） | ↓L2 SDK，↓L1 进程，→devices.json |

### 3.1 对上（L4）的接口全景

**统一响应包络**：`{ok: bool, error?: str, ...数据}`；admin 接口鉴权头 `X-Auth-Token`（登录 POST /admin/login `{username, password}` 发 token，内存态重启失效）。

| 组 | 端点 | 说人话 |
|---|---|---|
| 查询 | GET /health · /devices · /status · /fleet/status · /track · /audit/recent | 读缓存/档案 |
| 控制 | POST /command `{device_id, cmd, speed, angle}` | 换算 MOVE→vx,vy → CreateCommand → 乐观回显；冻结 403；当前语义=已受理 |
| 实时 | WS /ws | fleet_state 帧 `{type, ts, cars:[{device_id,name,color,online,x,y,heading,speed,battery,time}]}` |
| 管理 | POST /admin/login · GET /admin/overview · /admin/devices · /admin/commands | 登录/总览/花名册/命令历史 |
| 管理 | POST /admin/devices（注册）· /freeze（冻结）· DELETE /admin/devices/<did>（注销） | 改注册表+SDK |
| 管理 | GET /admin/cloud/devices（对账）· DELETE /admin/cloud/<did>（清残留） | ListDevices 对比 |
| 管理 | POST /admin/devices/<did>/start · /stop | 拉/杀 L1 进程 |
| 页面 | GET /monitor/view · /admin/view · /track/view · /console/view | 动态供 HTML |

### 3.2 对下（L2）的接口

见 §2 SDK 表。所有云端访问**只能**经 `IoTDA SDK 封装` 模块（app.py 内的 cloud_* 函数），其他模块不得绕过。

## 4. L4 客户端层 —— 三种顾客

| 客户端 | 消费的接口 | 本地状态 | 角色定位 |
|---|---|---|---|
| monitor.html 监控大屏 | WS /ws（收帧）+ POST /command（摇杆）+ GET /devices | fleet 字典、obs/disp 航位推算表、trails 轨迹尾线 | 观察者+操控 |
| admin.html 管理后台 | 全部 /admin/* + 4 个展示路由（token 存内存） | token、当前页签 | 管理员（PC+APP 内嵌共用） |
| track_demo.html 轨迹回放 | GET /track + GET /devices | 选车/时间窗 | 查档案 |
| CarFleet APP | FleetClient：800ms 轮询 /fleet/status、POST /command、GET /track；Web 组件内嵌 /admin/view | selectedId（Preferences 持久化）、FleetCar 列表 | 操作者 |

**页面端内部约定（L4 内的"软接口"）**——分段航位推算对帧语义的依赖：
- 帧 x/y 变化 = **真实位置修复** → 推算起点对齐观测
- 帧仅 heading/speed 变化 = **命令回显** → 起点沿旧方向推进 dt 再换向（与真车运动一致）
- 帧来自乐观回显和影子回报，两者共用一个 fleet_state 格式，页面靠"什么字段变了"来区分——这是 L3 回显设计与 L4 渲染设计之间的隐式契约。

## 5. 层间连接一览（每条连接的协议、方向、内容、节奏）

| # | 连接 | 协议 | 方向 | 内容 | 节奏/触发 |
|---|---|---|---|---|---|
| ① | L4→L3 | HTTP REST | 请求 | 查询/命令/管理 | 用户操作+APP 800ms 轮询 |
| ② | L3→L4 | HTTP 响应 | 应答 | 包络 {ok,...} | 即时 |
| ③ | L3→L4 | WebSocket | 推送 | fleet_state 帧 | 事件驱动+0.5s 兜底 |
| ④ | L3→L2 | HTTPS SDK | 调用 | ShowDevice/Shadow/CreateCommand/Add/Delete/List | poll 2s + 命令时 + 管理操作时 |
| ⑤ | L2→L3 | HTTPS 响应 | 应答 | 在线状态/影子属性/command_id | 即时 |
| ⑥ | L1→L2 | MQTT | 上报 | car_status 属性 | 5s/60s/命令后≤2s |
| ⑦ | L2→L1 | MQTT | 命令 | car_control move/stop | 有命令即转 |
| ⑧ | L3→L1 | subprocess | 运维 | 启动/终止模拟器进程 | 点上线/下线按钮 |
| ⑨ | L1→L3 | 本地 HTTP | 调试 | /state 实时状态 | 仅调试，正式链路不用 |

**配额约束贯穿 ⑥⑦**：IoTDA 免费单元约 1 万条/日 → ⑥ 的节奏不可调快，所有"流畅度"优化只能在 ③④ 和 L4 内做（乐观回显+航位推算）。

## 6. 三个跨层场景（把五张连接全串起来）

### 场景 A：管理后台点"上线"（⑧①④⑥）
```
L4 admin → POST /admin/devices/<did>/start
L3 admin → 扫描命令行特征：有僵进程先清 → subprocess 拉起 L1 进程
L1 进程 → 读 devices.json → MQTT 连 L2 → 影子/在线状态变 ONLINE
L3 poll_loop → 2s 内抄到 online=true → L4 大屏/APP 显示"在线"
（全程约 3s：MQTT 建连 + 云端判活 + 缓存轮询）
```

### 场景 B：拖动摇杆（①②④⑦⑥③）
```
L4 摇杆 → POST /command {MOVE, angle, speed}
L3 → 校验（注册/冻结/参数）→ SDK CreateCommand → 云受理
   → 乐观回显写缓存 + WS_DIRTY 立即推帧（快通道 ≈0.33s 到画面）
L2 → MQTT 转发 move(vx,vy) 给在线的 L1
L1 → on_message 立即执行 → CarSim 换向 → 事件补报属性（≤2s）
L3 poll_loop → 影子值变化 → 清回显守卫 → 真实数据接管（慢通道 ≈2s 确认）
L4 → 全程航位推算连续渲染（回显=换向、观测=校准，见 §4 软接口）
```

### 场景 C：注册一辆新车（①④⑧）
```
L4 admin 填 node_id → POST /admin/devices
L3 → SDK DeleteDevice（清可能残留）→ AddDevice（云端建档）
   → devices.json 追加（自动分配颜色/出生点/8081+N 端口）→ 返回一次性密钥
   （此后点"上线"即走场景 A）
```

## 7. 改动指南（按层定位）

| 想改什么 | 动哪层 | 是否影响其他层 |
|---|---|---|
| 页面样式/布局/推算参数 | L4（web/*.html） | 零影响，刷新即生效 |
| 新增接口/改缓存策略/管理功能 | L3（app.py） | 重启后端；L4 若用新接口需同步改 |
| 换云厂商/改 SDK 调用 | L3 的 cloud_* 封装 | L1/L4 零改动 |
| 车的运动手感（速度上限/电量） | L1（CarSim 参数） | 零影响 |
| **真车接入** | 只换 L1 | L2/L3/L4 零改动（协议合同的价值） |
