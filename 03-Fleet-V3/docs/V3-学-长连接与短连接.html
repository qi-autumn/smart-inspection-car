先给结论

一句话：区别不在于"这根线连了多久"，而在于一次握手能说几句话、以及谁可以先开口。短连接＝一问一答，答完就挂；长连接＝接通后一直不挂，双方随时都能说话，服务端可以主动推。

生活比喻：短连接像发短信——每发一条都要重新写收件人、等回复、结束；长连接像打电话——拨通一次，之后谁想说就说，直到有人挂断。项目里 APP 每 800ms 发一条"短信"问状态，网页大屏则是打通了"电话"等着后端念稿。

先纠正一个最容易混淆的点：HTTP/1.1 默认开启 Connection: keep-alive，会复用底层 TCP 连接，但它在语义上仍是短连接（每次还是"请求 → 响应"的一问一答，服务端不能主动开口）。"TCP 复用" ≠ "长连接"。真正的长连接要看有没有"服务端主动推"的能力：WebSocket、MQTT、SSE 才算。
1

看图理解

WebSocket 有个特别之处：它借 HTTP 完成开场（发一个带 Upgrade: websocket 的请求），握手成功后这条 TCP 连接就"改行"了，不再是 HTTP。所以代码里能看到 ws:// 与 http:// 共用同一个端口 8000。

一个重要的连带结论

项目里"车在线"这件事本身就是长连接的副产品：MQTT 连着 = ONLINE，断开 = OFFLINE（靠 keepalive=60 心跳判定）。后端用 ShowDevice 查到的"在线"，其实是云端在替你看这根长连接是否还活着。这也是为什么"下线"按钮必须去杀掉模拟器进程——只有断开长连接，云端才会改状态。

代码对照：短连接长什么样、长连接长什么样

均摘自当前工程
短连接 ① APP 每 800ms 发一次"短信"
CarFleet/.../net/FleetClient.ets : 55~62、89~96
// 每一次请求都 createHttp() 新建一个请求对象
const req = http.createHttp();
const resp = await req.request(`http://${host}:${port}/fleet/status`, {
  method: http.RequestMethod.GET,
  connectTimeout: 5000,
  readTimeout: 5000
});

// connect() 里用定时器不断重复这个"一问一答"
this.baseUrl = `http://${host}:${port}`;
await this.fetchFleet(host, port);   // 先探活
this.timerId = setInterval(() => { this.pollOnce(); }, POLL_INTERVAL_MS);  // 800ms

特征：请求里带完整 URL + 方法 + 超时，拿到 responseCode === 200 就结束。setInterval 只是把很多次短连接串起来，并没有把它们变成一根长连接。

课堂对应：请求-响应模型、无状态（服务端不记得上一次请求是谁，所以 APP 每次都要把选中的车 ID 一起发）。
短连接 ② 网页发命令 / 后端查云端
web/monitor.html : 194~197　server/app.py : 135~140
// 网页：相对路径，一次 fetch 一次往返
const r = await fetch("/command", { method: "POST",
  headers: { "Content-Type": "application/json" }, body: JSON.stringify(body) });

# 后端：SDK 每次调用都是一次独立的 HTTPS 请求
def cloud_show_status(device_id: str) -> str:
    req = ShowDeviceRequest()
    req.device_id = device_id
    resp = CLIENT.show_device(req)          # 请求 → 响应 → 结束
    return getattr(resp, "status", "UNKNOWN")

特征：无会话状态。后端每 2 秒对每台车重复一遍这个调用，云端并不"记得"上次是谁问的；鉴权靠每次请求里的 AK/SK 签名。

长连接 ① 网页 ↔ 后端的 WebSocket
server/app.py : 668~678　web/monitor.html : 130~158
# 服务端：每个客户端一个线程，一根连接上反复 send
@sock.route("/ws")
def ws_fleet(ws):
    try:
        while True:
            ws.send(fleet_state_message())          # 主动推，不等客户端问
            WS_DIRTY.wait(WS_BROADCAST_INTERVAL)    # 0.5s 兜底 / 事件立即唤醒
            WS_DIRTY.clear()
    except Exception:
        logging.info("[WS] 客户端断开，广播线程退出")

// 客户端：只建一次，之后靠回调收数据
ws = new WebSocket(`${proto}://${location.host}/ws`);
ws.onmessage = ev => { const msg = JSON.parse(ev.data); ... };

特征：while True + ws.send() —— 服务端想推就推，客户端用 onmessage 被动接收。一根连接、N 次数据。

配套机制（长连接必须有）：断线要重连，且不能疯狂重连。项目用的是指数退避：
ws.onclose = ws.onerror = () => {
  const delay = Math.min(1000 * 2 ** wsRetry, RETRY_MAX_DELAY);
  wsRetry++;
  setTimeout(wsConnect, delay);
};
长连接 ② 设备 ↔ 云端的 MQTT
device/car_mqtt_client.py : 153~157、253~272
# 连一次，之后一直挂着；keepalive=60 表示心跳周期
mqttc.connect(cloud_cfg["mqtt_host"], cloud_cfg["mqtt_port"], keepalive=60)
mqttc.loop_start()                                  # 后台线程维持这根长连接

# 连上后订阅命令 topic，云端随时可以主动下发
def on_connect(client, userdata, flags, reason_code, properties):
    if reason_code == 0:
        client.subscribe(f"$oc/devices/{DEV['device_id']}/sys/commands/#", qos=1)
        connected.set()

# 断线自动重连（同样是指数退避）
mqttc.reconnect_delay_set(min_delay=1, max_delay=30)

特征：loop_start() 会开一个后台线程持续收发心跳；on_message 是回调，云端命令到达时被动触发。如果这里改成短连接，云端就永远没法主动叫到车（设备没有公网地址，也不该一直轮询云端）。

优缺点对照表

维度短连接（HTTP 请求-响应）长连接（WebSocket / MQTT）
建立开销每次都要 TCP 三次握手（HTTPS 还要 TLS 握手）；高频时浪费明显只握手一次，之后零建连成本
实时性取决于轮询间隔；APP 800ms、后端 2s，天然滞后服务端一有新数据立刻推，项目里命令回显约 0.33s 到画面
谁先开口只能客户端先问，服务端不能主动找客户端双向，服务端可主动下发命令 / 推帧
服务端资源无状态、易横向扩展；请求完就释放每个客户端要占一个连接 + 线程/内存，连接数上去要专门优化
状态保持无状态，参数每次都要带全（device_id、token）有会话，可记住"这个连接属于谁"；但要自己管心跳与重连
断线处理简单：这次请求失败就重试，没有"连接"要维护复杂：心跳、超时判定、指数退避、半开连接、消息补发都要考虑
穿透与兼容最通用，任何代理 / 防火墙 / CDN 都认可能被代理或 NAT 超时掐断；移动端切网络容易掉线
调试难度低：curl、浏览器 F12 一条条看得清清楚楚高：要看帧流、心跳、重连日志
典型场景查数据、提交表单、下载文件、调用第三方 REST API聊天、实时行情、在线游戏、IoT 设备管控、实时监控大屏
项目里的例子APP 轮询、fetch /command、SDK 查影子、/state 旁路、test_api 自测/ws 广播、MQTT 8883 上下行
别把"长连接"当成绝对更好：它用"服务端资源 + 断线复杂度"换"实时性 + 可推送"。项目里 APP 就故意选了短连接——因为手机上网络会切换、APP 会退到后台，维护长连接的收益抵不上复杂度。
5

怎么选：一张决策清单

选短连接，如果……

  • 操作是"我问你答"（查询、提交、下单、调第三方 API）
  • 数据几秒变一次，秒级延迟可接受
  • 客户端数量多但活跃度低（省服务端连接）
  • 要穿过各种代理 / 要最简单好调试
  • 运行在手机后台、网络常切换

选长连接，如果……

  • 服务端需要主动开口（云端要下发命令给车）
  • 数据变化频繁且要求"立刻可见"（监控大屏 10Hz）
  • 需要感知对端"在不在"（在线/离线状态）
  • 同一次会话要来回说很多句，重建连接不划算
  • 愿意承担心跳、重连、连接数管理

还有个中间方案：SSE / 长轮询（本项目没用，但值得知道）

长轮询：客户端发一个请求，服务端"憋着"不回，直到有数据或超时才响应，客户端立刻再发一个——用短连接模拟推送。SSE（Server-Sent Events）：一根 HTTP 长连接，只允许服务端单向推文本。两者都比 WebSocket 简单，但都不支持双向。项目里因为要"服务端推 + 命令双向"，直接选了 WebSocket 和 MQTT。

本项目为什么混用（最值得记住的一节）

位置选择真实原因
设备 ↔ IoTDA长（MQTT）设备在 NAT 后面、没有公网地址，只有它自己先连上云端并保持住，云端才能随时下发命令。这不是偏好，是物理约束。附带白送了"在线/离线"信号。
大屏 ↔ 后端长（WS）后端有"乐观回显"要立刻送出去；若改用轮询，最快也要等下一次请求，0.33 秒的跟手感就没了。
APP ↔ 后端短（800ms 轮询）ArkTS 的 HTTP 接口最简单、教学项目优先可读性；手机网络切换/后台时不必维护长连接。代价是 APP 比网页慢半拍（0.8s）。
后端 ↔ 云端 SDK短（HTTPS）华为云应用侧本来就是 REST API，没有推送通道可选；配额也限制调用频率，2 秒一轮足够。
后端 → 模拟器 /state短（本机 10Hz）127.0.0.1 回环，建连成本近乎为零；用线程池并发拉取就够快，不值得为它加长连接。

如果你想把 APP 也改成 WebSocket（练习方向）

后端 /ws 已经现成，不用改服务端。APP 侧要做三件事：① 在 FleetClient.ets 里用鸿蒙的 WebSocket 接口（@ohos.net.webSocket）建立连接并订阅 fleet_state 帧；② 把 setInterval(pollOnce) 换成 on('message') 回调解析同一份 cars 数组；③ 补心跳与指数退避（可照抄 monitor.html 的 wsConnect）。收益：APP 画面从 0.8 秒一步变成与网页同步；代价：要重构建 APP、要处理后台断线。

7

常见坑 + 自测

容易踩的坑

  • 以为 keep-alive 就是长连接——它只复用 TCP，服务端仍不能主动推。
  • 长连接忘了心跳：MQTT 的 keepalive=60、WS 的定期帧，缺了会被 NAT 静默掐断。
  • 长连接忘了重连退避：后端重启时几十个页面同时每秒重连，形成风暴。
  • 以为短连接"关了就查不到状态"：状态在后端 STATE_CACHE 里，与连接无关。
  • 把"下线"理解成改数据库字段：必须断开 MQTT 长连接（杀进程），云端才会判离线。
  • WS 客户端用了 ws:// 却访问 https 页面：会触发混合内容拦截，要用 wss://（项目里已有 location.protocol 判断）。

与前后知识点的连接

  • 往前：接《技术栈与文件地图》里的 flask-sock / paho-mqtt。
  • 平行：另一份《HTTP 与 HTTPS》讲"这根线加不加密"，本份讲"这根线挂不挂断"——两个维度别混。
  • 往后（线）：「控车时序图」里快通道依赖 WS 长连接、慢通道依赖 MQTT 长连接，短连接只负责发命令那一瞬间。

自测小问题

1. HTTP/1.1 的 keep-alive 算长连接吗？为什么？

不算"长连接语义"。它只是让多次请求复用同一条 TCP，省掉重复握手；每次交互仍是"客户端请求 → 服务端响应"，服务端无法在客户端没问的时候主动发数据。判断标准看"能否服务端主动推"。

2. 为什么设备侧不能用短连接？

因为车在局域网/NAT 内、没有可被云端主动访问的地址；只有设备先建立并保持一条长连接，云端才有通道把 move/stop 命令推下来。另外在线/离线判定也依赖这条连接的心跳。

3. 项目里哪条链路是"看起来高频但其实仍是短连接"？

APP 的 800ms 轮询，以及后端 10Hz 拉模拟器 /state。两者都是"每次新建请求、拿到响应即结束"，高频只是把很多次短连接排得很密。

4. 长连接最大的代价是什么？项目怎么应对？

代价是服务端要为每个客户端保持连接/线程，且必须处理断线。项目应对：WS 每客户端一个线程 + WS_DIRTY 事件唤醒（避免空转）、指数退避重连；MQTT 用 paho 自带的 loop_start() + reconnect_delay_set。

5. 如果把 APP 改成 WebSocket，后端要改吗？

不需要，/ws 已存在且广播的是与 /fleet/status 同源的 cars 数据。只需改 APP 的 FleetClient 并重新构建，再补心跳与重连。
