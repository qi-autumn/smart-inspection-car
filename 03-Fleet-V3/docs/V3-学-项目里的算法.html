先给结论

一句话：这门课在项目里几乎全用上了，但不是排序、动态规划、图论那类"竞赛型算法"，而是数值积分、哈希查找、增量检测、平滑滤波、环形数据处理、倍增退避这些"工程型算法"；数据结构主要是哈希表（字典）+ 数组/队列 + B 树索引。

生活比喻：数据结构决定"东西怎么摆"——项目把每台车按车牌号放进一个字典，找车不用挨个翻；算法决定"怎么算"——车下一秒在哪，靠的是拿上一帧位置加一小段位移，反复算。整部项目其实就在做两件事：快速找到状态、把稀疏的状态算成连续的画面。

为什么看不到"经典算法"

因为业务规模太小（4 台车、每车几百个轨迹点），O(n) 和 O(log n) 的差别是微秒级。工程里优先选好读、好改、不容易出 bug 的写法，而不是理论最优。第 4 节会诚实指出三处"本可以更快但没必要"的地方。

怎么读这份文档

每一节固定四块：真实代码 → 逐行解释 → 对应课程知识点 → 解决了什么问题（不用会怎样）。建议开着源码对照，看到 文件:行号 就跳过去看上下文。

② 数值积分（欧拉法）：让车真的"走起来"
device/car_mqtt_client.py : 79~89　常量 TICK_HZ = 20、MAX_SPEED = 1.5
def tick(self, dt: float) -> None:
    with self.lock:
        speed = math.hypot(self.vx, self.vy) * MAX_SPEED
        if speed > 0.01 and self.battery > 0:
            self.x += self.vx * MAX_SPEED * dt
            self.y += self.vy * MAX_SPEED * dt
            self.theta = math.degrees(math.atan2(self.vx, self.vy)) % 360
            self.battery = max(0.0, self.battery - BATTERY_DRAIN_PER_SEC * dt)
        else:
            self.vx, self.vy = 0.0, 0.0

逐行解释：这就是最朴素的显式欧拉积分——"新位置 = 旧位置 + 速度 × 时间步长"。20Hz 意味着 dt = 0.05s。举例：摇杆向东满速的一半，vx=0.5，则每 tick x += 0.5 × 1.5 × 0.05 = 0.0375 米，一秒走 0.75 米。

前端的 estPos()（monitor.html : 311~326）用的是同一个公式的"一次性版本"：dist = ev * dt，只是不逐帧累加，而是从观测点直接推算到当前时刻。

对应课程：递归/迭代思想、数值计算入门。这里没有闭式解，靠"重复执行小步骤"逼近连续运动——和课堂上写 for 循环求和是同一类思维。
解决什么问题：把"速度"这个抽象的指令，变成屏幕上会动的位置。不用会怎样：车只会在收到上报时瞬移一格，也就是项目早期"一顿一顿"的观感。

对应课程：数学（三角函数、极坐标与直角坐标互换）；"单位向量 / 模长"属于线性代数入门。代码里的 hypot 就是勾股定理。
解决什么问题：让 APP 摇杆、网页摇杆、后端协议、设备固件四端对"方向"有唯一定义。这也是第⑧步换真车必须原样保留的契约——约定错了，车会朝反方向跑（项目早期就修过一次 APP 与网页朝向不一致）。
④ 一阶低通滤波（指数平滑）：消除画面跳变
web/monitor.html : 342~357
const fdt = Math.min((now - lastFrame) / 1000, 0.1);
for (const c of list) {
  const t = estPos(c.device_id);
  const s = disp[c.device_id] || (disp[c.device_id] = { x: t.x, y: t.y, heading: t.heading });
  const k = Math.min(1, fdt * 8);
  s.x += (t.x - s.x) * k;
  s.y += (t.y - s.y) * k;
  let dh = t.heading - s.heading;              // 航向角按最短弧平滑
  while (dh > 180) dh -= 360;
  while (dh < -180) dh += 360;
  s.heading += dh * k;
}

逐行解释：s += (目标 - s) × k 是标准的一阶低通滤波。60fps 时 fdt≈0.0167，k≈0.133，即每帧只消掉 13% 的误差，于是位置变化被"摊"到若干帧里，眼睛看到的是滑过去而不是跳过去。

对应课程：递推式 / 迭代逼近；也可理解为"加权平均"，新值权重 k、旧值权重 (1-k)。（信号处理课里叫 EMA / 一阶 IIR。）
解决什么问题：真实观测每 5 秒才到一次，且带修正；直接把坐标设为观测值会看到闪现。不用会怎样：车每隔几秒"瞬移"一下，正是用户反复反馈的不流畅。
⑤ 环形数据归一化：角度不是普通数字
web/monitor.html : 353~355（上面代码里那两个 while）
let dh = t.heading - s.heading;
while (dh > 180) dh -= 360;
while (dh < -180) dh += 360;

逐行解释：角度是模 360 的环形量。从 350° 转到 10°，数值差是 -340°，但物理上只转了 +20°。这两行把差值折回 [-180, 180] 区间，即"最短弧"。同理 % 360（Python）和 round(float(angle)) % 360（app.py : 190）都在做归一化。

对应课程：模运算、环形数组 / 循环队列里"下标回绕"的同款思想；也常出现在时钟、星期、罗盘的计算题里。
解决什么问题：转向时车头平滑转过最短路径。不用会怎样：从 350° 调到 10° 会让车在空中倒转一大圈，视觉上像甩尾。

逐行解释：两个不同层次的"去重"。前端用 lastSeen 字典记住每台车最后一个点（哈希 + 增量比较）；后端用 TRACK_LAST 记住上次入库的元组，任一字段变化超阈值才插行——因为静止时设备每 60 秒还会重复上报，不设阈值就会堆一堆一模一样的点。

数据库侧还有一道"保留最近 N 条"的窗口清理（track_store.py : 63~68）：ORDER BY ts DESC LIMIT 1 OFFSET ? 找出第 20000 条的时间，把更早的删掉；再加 7 天过期。

对应课程：队列 / 滑动窗口；"只与前一个状态比较"属于增量思想；阈值判断属于浮点误差处理（不能直接用 == 比浮点数）。
解决什么问题：内存和磁盘都有上限。诚实点评：JS 数组的 shift() 是 O(n)（后面元素要整体前移），严格说该用环形缓冲区做到 O(1)；但这里 n=150、4 台车、每帧最多一次，代价可忽略——这就是典型的工程取舍。

逐行解释：第 1 次等 1s、第 2 次 2s、第 3 次 4s……上限 30s；连上后 wsRetry = 0 归零。这就是 2^n 的倍增（指数退避）。

对应课程：倍增思想（二分/快速幂里也用）、贪心策略的一个极简例子；复杂度上"重连次数"随故障时长变成 O(log T)。
解决什么问题：后端重启或网络抖动时，几十个页面同时每秒重连会形成"重连风暴"。不用会怎样：固定 1 秒重试也能用，但服务端一恢复就被瞬时压满。

⑩ 分段航位推算：项目里最完整的"自研算法"
web/monitor.html : 285~326（applyObs + estPos）
const posChanged = o.fx !== x || o.fy !== y;
const motionChanged = o.eh !== heading || o.ev !== speed / 100 * MAX_SPEED_MS;
if (!posChanged && !motionChanged) return;   // 同一份缓存广播，不动外推时钟
const dt = Math.min((now - o.t0) / 1000, STALE_S);
if (posChanged) {
  o.fx = x; o.fy = y; o.ex = x; o.ey = y;      // 真实修复：起点对齐观测
} else {                                       // 回显：起点沿旧方向推进 dt 再换向
  o.ex += Math.sin(o.eh * Math.PI / 180) * o.ev * dt;
  o.ey += Math.cos(o.eh * Math.PI / 180) * o.ev * dt;
}
o.eh = heading; o.ev = speed / 100 * MAX_SPEED_MS; o.t0 = now;

逐行解释：它把前面 ①~⑤ 全用上了——字典存状态（①）、欧拉积分推进（②）、三角函数分解（③）、外推（④）、角度处理（⑤）——核心是一条分类讨论：x/y 变了 = 真实观测，重置起点；只有朝向/速度变了 = 命令回显，起点沿旧方向走到"此刻"再换向。

对应课程：状态机（每个车维护自己的状态对象）、分类讨论、时间差计算。这是全项目最值得精读的一段，因为它体现了算法服务于业务语义，而不是套模板。
解决什么问题：把"5 秒一个真实点"和"0.25 秒一条命令回显"缝成连续折线。写错会怎样：把回显也当成新观测去重置位置，车会每 250ms 被拉回旧位置——这正是之前"越改越抖"的那个 bug。

课程知识 → 项目落点对照

含"没用到"的诚实说明
课程章节项目里用到了吗具体落点
线性表 / 数组大量轨迹点数组、车队列表、时间窗 WIN_MINUTES、颜色池 CAR_COLORS
栈 / 队列轻用轨迹尾线是"先进先出"的滑动窗口；没有显式栈结构
哈希表核心STATE_CACHE、fleet、obs、disp、trails、DEV_META、TRACK_LAST、ECHO_PENDING、TOKENS 全是字典
树 / B+ 树间接SQLite 索引 idx_track_dev_ts，代码里没有自己实现树
查找 / 排序轻用字典查找 O(1)；SQL ORDER BY ts ASC 走索引；无手写快排/归并
贪心 / 倍增有指数退避 2 ** wsRetry；自适应缩放取 min(W/w, H/h)
递归 / 分治没有业务都是扁平循环，刻意避免递归以降低初学门槛
图论没有网络拓扑"看起来像图"，但代码里没有任何图算法（没有路径规划、没有最短路径）——第⑦步 AI 导航若加入寻路，这里就会用上
动态规划没有状态简单，无最优子结构问题
数值计算 / 几何核心欧拉积分、三角函数、atan2、勾股距离、向量归一化、模运算
并发数据结构有threading.Lock 保护共享字典；threading.Event（CMD_DIRTY / WS_DIRTY）做生产者-消费者通知

给你一个延伸思考

项目里唯一"像算法题"的空白是路径规划：现在的车只会"朝一个方向直走"，没有目标点、没有避障、没有地图。如果第⑦步要加"自动巡检到指定点"，就会用到 BFS / A* / Dijkstra —— 那时你的数据结构与算法课会真正派上大用场。这也是为什么现在看项目"算法不多"：它目前只解决了通信与展示，还没解决智能决策。

工程权衡：三处"本可以更快，但没必要"

Array.shift() 是 O(n)

轨迹超长时删最旧点，理论上环形缓冲 O(1) 更优。但 n≤150、最多 4 台、每帧一次，实测毫无影响。可读性赢了。

时间窗 filter 是 O(n)

点已按 ts 升序，二分找起点可到 O(log n)。但几百个点省不下 1ms，还多出边界 bug 风险。

每帧求 min/max 是 O(n)

车数 n 极小，60fps × 4 次比较完全免费。若将来上千台车，才需要考虑增量维护包围盒。

但有两处"必须"优化

① 按 ID 查状态用字典而不是遍历 —— 因为访问频率是每帧每车多次；② 轨迹查询建索引 —— 因为数据在磁盘上，全表扫描差的是数量级。判断标准：数据在哪、被调用多频繁。

初学者最容易误学的一点：不要因为"学过二分"就到处改 O(n)。工程里优化的前提是先测出瓶颈。这个项目真正的瓶颈从来不在算法，而在网络（5 秒上报、2 秒轮询）——所以前面所有改造都花在了"链路"上，而不是把 filter 改成二分。

常见坑 + 自测

与这些代码相关的坑

  • 浮点数不能用 == 比较：所以 _track_changed 全用 > 0.005 阈值。
  • 角度必须归一化：350°→10° 的差值要走最短弧，且 atan2 的参数顺序是 (vx, vy) 才能符合"0=正北"。
  • 外推时钟不能被重复广播重置：同一份缓存每秒推多次，必须先用"状态是否变化"判断（分段推算第 297 行）。
  • 字典键要用完整 device_id：did.split("_", 1)[1] 按第一个下划线切，用错会切出产品 ID。
  • 共享字典在多线程里必须加锁：CACHE_LOCK / CarSim.lock 不是装饰。

自测小问题

1. 为什么项目里到处是字典，却几乎看不到数组查找？

因为所有检索都按 device_id 这个唯一键进行，哈希表平均 O(1)；数组需要遍历比较 O(n)，且每帧要查多次。字典同时也让"每台车独立维护外推状态"这件事写起来最自然。

2. tick() 里的 dt 是谁给的？改成 10Hz 会怎样？

由 20Hz 的循环给出 dt≈0.05s。改成 10Hz（dt≈0.1s）位置精度下降一半、轨迹点变粗，但车的速度不变（因为位移 = 速度 × dt，步长变大、步数变少）。这正是欧拉积分的特性。

3. 指数平滑里的 k 越大越小分别是什么效果？

k 大 → 跟得紧、几乎不平滑（k=1 时直接跳到目标）；k 小 → 更顺滑但落后更多。项目取 fdt*8，约 0.13/帧，在"跟手"和"不跳"之间折中。

4. 把 trails.shift() 换成环形缓冲值得吗？

当前规模不值得：150 点 × 4 台 × 最多每帧一次，成本可忽略，还更好读。只有车数或点数量级上升（比如上千点做全轨迹回放）才值得改。这就是复杂度分析的实际用法：先估算规模，再决定要不要优化。

5. 项目里哪个知识点最接近"状态机"？

applyObs：每台车有自己的状态对象（外推起点、朝向、速度、观测时刻），输入分"真实修复 / 命令回显 / 无变化"三类，分别做不同迁移。另外 CarSim 本身也是一台状态机（vx/vy 决定行驶或静止）。
