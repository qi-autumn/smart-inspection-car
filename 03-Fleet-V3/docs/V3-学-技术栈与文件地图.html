先给结论

一句话：这个项目的技术栈其实很"轻"——没有数据库服务器、没有前端框架、没有消息队列中间件。全靠 Python 标准库 + 三个第三方库（paho-mqtt / Flask / 华为云 SDK），加一个 SQLite 文件、几页原生 HTML、一套鸿蒙 ArkTS，就把"多车—云端—后端—多端界面"串起来了。

生活比喻：这像一家小店——骑手用对讲机（MQTT）报位置，总部有块记录板（设备影子），店里的客服（Flask 后端）拿一个抄写本（STATE_CACHE）和一个账本（SQLite），顾客看的是手绘地图（Canvas 网页）和手机 App（ArkTS）。没有一项技术是"为了炫技"，每一项都是为了解决一个具体的卡点——这也是读技术栈时最该抓住的线索。

判断"主文件"的三条标准

① 后端启动时会不会 import 它；② 页面路由会不会指向它；③ 模拟器启动时会不会读它。三条中任意命中一条 = 运行时必需的主文件。

"过程性文件"是什么

开发过程中为了验收某一步 / 造演示数据 / 记录设计而写的，系统跑起来之后不依赖它们。删掉不影响运行，但删掉就看不出项目是怎么一步步长出来的。

还有一类容易误判

运行时自动生成的产物（fleet.db、commands.log、__pycache__、build/）。它们不是源码，不该手改，也不算主文件。

面

L1 模拟小车
Python 3paho-mqttssl / TLS 8883 hmac + hashlibthreading http.serverargparseJSON

云端不跑我们写的代码，只提供三种能力：接入、存最后一次上报、转发命令。配额约 1 万条/日，是很多设计取舍的源头。
L3 业务后端

全系统枢纽：一个进程里同时跑 HTTP 服务、轮询线程、旁路线程、WebSocket 推送线程，共用一份带锁的缓存。22 个 REST 端点 + 1 个 WS 端点。
L4 客户端
原生 HTML/CSS/JS（无框架）Canvas 2D requestAnimationFrameWebSocket API / fetch CSS Grid + media querylocalStorage HarmonyOS ArkTS / ArkUI@ohos.net.http @ohos.data.preferences@ohos.web.webview
网页走"浏览器原生能力 + 自研航位推算算法"；APP 走 ArkTS 声明式 UI + 800ms HTTP 轮询。两边都不直连云端。
工具链
Windows .bat 启动脚本DevEco Studio（hvigor 构建 / 签名） curl + Python 自测脚本node --check（JS 语法校验）
没有 CI/CD、没有容器、没有包管理锁文件（除鸿蒙工程自带的 oh-package）。属于教学项目刻意保持的简单度。
为什么没用 MySQL / Vue / React / Redis？ 因为这是教学项目：状态量小（4 台车）、单机运行、需要学生能一眼看全链路。SQLite 一个文件、原生 JS 一个页面、内存缓存一个字典，比引入框架更利于"看得见"。这不是技术落后，是刻意控制复杂度。

逐模块技术表：每一项的作用

重点

2.1 设备模拟层 · device/car_mqtt_client.py

技术点用在代码里作用（去掉会怎样）
paho-mqttmqtt.Client()、loop_start()、subscribe/publishPython 的 MQTT 客户端库，负责与 IoTDA 建立长连接、订阅命令 topic、发布属性。没有它设备根本不在线，云端 ShowDevice 永远返回 OFFLINE。
ssl + 8883tls_set()给 MQTT 套 TLS 加密。IoTDA 设备接入端口 8883 要求加密链路，不配置会握手失败。
hmac / hashlib生成 MQTT 密码IoTDA 要求密码是"设备密钥 + 时间戳"的 HMAC-SHA256 结果，而不是明文密钥。算错就报 Bad user name or password。
threading.LockCarSim.lock运动线程（20Hz 改坐标）和上报线程（读坐标）并发，加锁保证读到的快照不是"半个更新"的脏数据。
20Hz 定时积分 TICK_HZ运动循环每 0.05 秒按 x += vx·dt 推一次位置，让车在进程内部是连续运动的。这是"实时"的真正源头。
三档上报节奏5s / 60s / 命令后 ≤2s在"云端消息配额"和"状态新鲜度"之间取平衡。事件补报让命令不必干等 5 秒周期才被看见。
ThreadingHTTPServer8081~8085 的 /state每车进程开一个本地调试口，吐内存里 20Hz 的真实状态。后端 10Hz 高速旁路读的就是它——屏幕丝滑的关键，也是 V2 当年流畅的原因。
argparse--device car_001一份代码跑出 N 台车，身份/密钥/出生点全从 devices.json 读。没有它就得多份复制粘贴的脚本。

2.2 云端接入与 SDK

技术点用在代码里作用（去掉会怎样）
设备影子ShowDeviceShadow云端替每台设备保存"最后一次上报的属性"。它是拉模式能成立的前提：后端随时来查都有数据，不必等设备此刻在线。代价是数据可能是几秒前的。
物模型服务 IDcar_status / car_control属性上报挂 car_status（x/y/theta/speed/battery），命令下发挂 car_control（move/stop）。挂错服务命令会石沉大海。
huaweicloudsdkiotda.v56 个 Request 类应用侧 REST SDK，让后端能查状态、查影子、下发命令、增删设备。后端与云端唯一的对话方式（网页/APP 都不碰它）。
BasicCredentials + DerivedCredentialsAK/SK 鉴权用账号 AK/SK 给应用侧 API 签名；with_derived_predicate 是 IoTDA 区域服务的特殊要求，漏了会鉴权失败。
Region(id, endpoint)客户端 builder指定 cn-north-4 实例和接入地址，SDK 才知道往哪台服务器发请求。
MQTT topic 约定$oc/devices/{id}/sys/...上报与命令的"信封地址"。这是将来换真车时必须原样照抄的合同，上面三层因此零改动。

2.3 业务后端 · server/app.py（1083 行，全项目最大）

技术点用在代码里作用（去掉会怎样）
Flask22 个 @app.get/post/delete提供 REST 服务与静态页面路由。所有客户端唯一的入口（:8000）。没有它网页和 APP 都无处可连。
flask-sock@sock.route("/ws")给 Flask 补 WebSocket 能力，服务端可主动推帧。没有它乐观回显无法即时送达，页面只能退回轮询。
后台线程 + 带锁缓存poll_loop / STATE_CACHE / CACHE_LOCK轮询线程每 2 秒抄云端影子写进字典，HTTP 线程只读字典。让"慢云端"和"快页面"解耦；加锁防多线程同时读写串数据。
ThreadPoolExecutorlocal_fast_loop10Hz 并发拉取各车 /state。串行时 3 个离线端口各等 0.15s 超时，会把 10Hz 拖成 2Hz——这是实测踩过的坑。
urllib.request本地旁路 HTTP 客户端直读同机模拟器进程内存状态，零云端消息，不违反 5s/60s 配额约束。可用 V3_LOCAL_FAST=0 关闭（真车接入时）。
乐观回显 + 回显守卫_echo_command_state / ECHO_PENDING命令被受理的瞬间把预期朝向写进缓存并立即推帧（约 0.3s 可见）；守卫拦住随后到达的旧影子，防止车"画了又跳回"。这是自研逻辑，不是任何库，专门解决跟手感。
subprocess + taskkill/admin/devices/{id}/start|stop后端在 PC 上拉起/终止模拟器进程。这是"APP 里点上线，车就在线"的原理，也是唯一由 L3 反向操作 L1 的受控通道。
secrets.token_hexadmin 登录 token生成随机令牌存在内存字典里，重启即失效。教学级鉴权，够用但不该用于生产。
JSON Lines 审计commands.log每条命令/管理操作追加一行 JSON，排查"谁在什么时候下了线"的第一现场。
统一响应包络{ok:true,...} / {ok:false,error}所有接口同构，客户端只需判一个字段。executed:true 表示云端已受理，不等于车已执行。

2.4 轨迹存储 · server/track_store.py

技术点用在代码里作用（去掉会怎样）
sqlite3 + WALfleet.db单文件嵌入式数据库，无需装服务。PRAGMA journal_mode=WAL 让读写并发不互相锁死；busy_timeout 防止偶发锁等待直接报错。
单进程一把 _LOCKinsert / query 串行路线图明确"不上多进程"，所以用一把线程锁把写操作串行化，换取实现简单、无竞态。
索引 idx_track_dev_ts按设备 + 时间查询轨迹回放按车 + 时间窗过滤，没索引数据量一大就会慢。
"变化才插行" + 治理7 天过期 / 单车 2 万条静止时 60s 的重复上报不产生重复点；定期清理防止 db 无限膨胀。

Canvas 2DgetContext("2d")画地图、网格、车形、轨迹折线。选它而非 DOM 元素，是因为几十台车 + 上百轨迹点用矢量绘制更轻、更可控。

WebSocket APInew WebSocket("/ws") + 指数退避重连大屏接收服务端推送；断线自动重连。APP 没用这个，走的是轮询。

3

八个最关键的技术点（单独拎出来记）

点

如果时间有限，先记住这八个。它们覆盖了项目里 80% 的设计意图，也是面试/答辩最容易被问到的地方。

① 设备影子（拉模式的地基）
L2 云端 · 由 app.py 的 ShowDeviceShadow 读取
云端为每台设备保存"最后一次上报"，后端随时来查都有值。
作用：让后端不必与设备同时在线也能拿到状态。代价：数据天然滞后几秒，后面所有"流畅度"工作都是在补这个代价。
② STATE_CACHE（唯一状态源）
L3 后端 · dict + threading.Lock
轮询线程写、HTTP/WS 线程读，全系统只有这一份状态。
作用：把"慢云端"和"快客户端"解耦。任何页面、APP、管理后台都不许自己问云端——这条铁律让多端天然一致。
③ 乐观回显 + 回显守卫
L3 后端 · _echo_command_state / ECHO_PENDING
命令受理即预测结果并推帧；守卫拦住随后到达的旧影子。
作用：把"命令 → 画面可见"从 2~5 秒压到约 0.33 秒，同时防止车"画了又跳回"。这是自研逻辑，项目里最巧妙的一处。
④ 本地高速旁路（10Hz /state）
L1↔L3 · ThreadingHTTPServer + ThreadPoolExecutor
后端并发直读模拟器内存里的 20Hz 真实状态。
作用：零云端消息、不破配额，让画面显示真实位置而非预测。仅模拟阶段有效，真车接入时用 V3_LOCAL_FAST=0 关闭。
⑤ 分段航位推算
L4 网页 · monitor.html 的 applyObs / estPos
真实观测对齐位置，命令回显只改朝向、起点沿旧方向推进。
作用：把低频观测点缝成 60fps 连续动画。若把回显当成新观测，车会每 250ms 被拉回旧位置——这正是之前"越改越抖"的 bug。
⑥ MQTT 物模型合同
L1↔L2 · car_status 上报 / car_control 命令
固定的 topic、服务 ID、属性字段、HMAC 鉴权。
作用：第⑧步换真车时，只要固件照抄这套报文，上面三层一行不用改。这是整个项目坚持协议约束的回报。
⑦ SQLite WAL + "变化才插行"
L3 存储 · track_store.py
单文件库、WAL 并发、只记真实影子观测、7 天/2 万条治理。
作用：历史数据保真（预测值绝不入库），回放页才有意义；同时避免静止时的重复数据撑爆库。
⑧ subprocess 反向管控设备
L3→L1 · /admin/devices/{id}/start|stop
后端按命令行特征拉起/终止模拟器进程。
作用：让手机 APP 能远程"上线/下线"PC 上的车。也是四层铁律唯一的受控例外——因为"在线"本质由设备 MQTT 连接决定，后端无法凭空改。

技术栈相关的常见坑 + 自测

容易踩的 8 个坑

  • ListDevices 的 device_id 过滤参数不生效 → 查在线必须用 ShowDevice；limit 上限 50，写 100 会报 400。
  • 命令体类名是 DeviceCommandRequest，不是文档里的 CommandBody。
  • 影子响应结构是 response.shadow[].reported.properties，值可能是 Decimal。
  • 命令 service_id 必须是 car_control，属性上报才是 car_status。
  • node_id 要按第一个下划线切（完整 ID 里产品 ID 也含下划线）。
  • 模拟器黑窗 = 车本体，关掉就下线；多个实例互踢会让命令被随机进程接收。
  • APP Web 组件吞掉原生 confirm()，弹窗必须自绘。
  • 8000 端口曾同时挂新旧两个后端进程（SO_REUSEADDR），改了代码没生效要先查进程。

自测小问题（点开看答案）

1. 为什么项目不用 MySQL，而用 SQLite 一个文件？

教学项目、单机单进程、数据量小（4 台车 × 变化才插行）。SQLite 零安装、零配置，WAL 已足够应付"一个线程写、几个线程读"。引入 MySQL 会多出服务、账号、连接池三件事，却不会带来收益。

2. paho-mqtt 和 huaweicloudsdkiotda 都是"连华为云"，区别在哪？

方向完全不同：paho-mqtt 是设备侧（模拟器/真车用，长连接、上报、收命令，走 8883）；SDK 是应用侧（后端用，HTTPS 短请求、查影子、下发命令、管理设备，用 AK/SK 鉴权）。两者从不混用。

3. 后端为什么要同时开 REST 和 WebSocket 两种服务？

REST 负责"客户端主动问"（查询、发命令、管理）；WebSocket 负责"服务端主动推"（状态变化、乐观回显即时送达）。只靠 REST 就得高频轮询，命令回显会有明显延迟。

4. ThreadPoolExecutor 在这里解决的是什么问题？

后端 10Hz 要拉 4 台车的 /state，没启动的车端口要等 0.15s 超时。串行时 3 个离线端口就吃掉 0.45s，刷新率掉到 2Hz。改成并发后超时重叠，仍能保持 10Hz。

5. 哪些文件可以放心删掉而系统照样跑？

B 类过程性文件（verify_step1.py、test_api.py、drive_cars.py、fleet_console.html 需同时去掉路由引用）和 C 类自动生成产物（__pycache__、构建目录）。但 devices.json、cloud_config.json、app.py、track_store.py、car_mqtt_client.py 一个都不能少。

6. 第⑧步接真车时，技术栈里哪一块会被替换？

只替换 L1：car_mqtt_client.py 由真车固件（同样的 MQTT 8883 + HMAC 鉴权 + car_status/car_control 报文）取代，同时用 V3_LOCAL_FAST=0 关闭只在本机有效的 /state 旁路、移除 subprocess 启停。L2/L3/L4 的代码与协议都不用改。
