V3 学习资料 · 仓库结构篇

一个仓库放三个版本，可行吗？

答案：完全可行，而且对你这个「教学演进型」项目更合适。源码 + 文档 + 配置模板进仓库、成品挂 Release 附件，这个划分也是对的。

已实测：三个版本无跨目录依赖 合计约 2.2 MB / 216 个文件 单仓库目录已备好 一次 init / commit / push 未执行任何 git 命令

1 一句话结论

能，而且我推荐你这个方案。一个仓库里放 01-TCP-V1 / 02-Cloud-V2 / 03-Fleet-V3 三个子目录，只提交源码、文档、配置模板；成品以 Release 附件分发。上一轮我给的是「三个独立仓库」方案，那只是其中一种选择，不是规定。

为什么单仓库更适合你：

  • 教学项目要展示的是「演进」：V1 → V2 → V3 放在同一个目录树下，别人一眼看懂三代关系；拆成三个仓库反而看不出承接。
  • 一个人维护、总量极小：三个版本合计约 216 个文件 / 2.2 MB，一个仓库毫无压力。
  • 别人只 clone 一次，cd 到对应子目录就能跑，不用记三个地址。
  • 操作减半：一次 init / commit / remote / push，不用重复三遍、也不用担心把 V3 推到 V1 的仓库里。
唯一要提前想清楚的一点：一个仓库只有一条 Releases 列表。三个版本的成品会混在同一个列表里，必须用 tag 前缀 + 附件名前缀区分（第 ⑦ 节给了命名约定）。另外，将来若只想公开某一代、另外两代保持私有，单仓库就不如三个仓库灵活。
但「Release 传成品」要沿用上一篇的结论：本项目已签名的 *.hap 绑定你板子的 UDID、且在实测 API 15 板子上启动崩溃，发出去别人既装不上也跑不起来。想练 Release 流程完全可以，但附件建议放未签名 HAP / 源码快照 / 演示素材包，并如实写已知限制；*.p12 私钥、真实配置、含密钥的 V3-Fleet-Complete.zip 绝不能当附件。

2 生活比喻：一本成长相册 vs 三本独立相册

三个独立仓库一个仓库三个子目录
比喻小学、中学、大学各一本相册，分放在三个书架上一本「成长相册」，三章按时间排好
看演进要把三本都找出来摊在桌上对比翻页就看到变化，接得上
借给人看给三个地址给一个地址
只想借其中一章直接给那一本，其余不外露整本都给人了（可撕页，但麻烦）
贴「成品标签」每本相册各贴各的，互不干扰只有一个标签板，得写清「第几章的成品」

Git / Release 在这个比喻里：Git 仓库 = 相册本身（每张照片什么时候贴的都有记录）；tag = 在某一页夹的书签（「V1 定版」「V2 冻结」）；Release = GitHub 网页上挂出来的「成品展示柜」，书签贴到哪个版本，柜子就对应哪个版本；附件 = 柜子里摆的实物。

关键理解：目录怎么摆，只影响「人和 Git 怎么找文件」，不影响小车怎么跑。三个子目录各自是独立的工作目录，先 cd 进去再运行脚本，彼此不会串。

3 在四层架构里的位置

再强调一次：仓库结构属于开发交付层，和运行时四层（设备层 → 云端层 → 业务后端层 → 客户端层）没有连线。把三个版本合进一个仓库，不会改动任何一行 app.py、Index.ets 或 MQTT 协议；断网、删仓库，小车照常开。

6 单仓库落地：完整命令

和上一篇《把项目上传到 GitHub · 手把手》的差别只有一处：只做一次，不用重复三遍。认证（PAT / SSH）、新建空仓库（不勾 README）、git status 肉眼核对这些完全一样。

第 1 步：本地复检

cd E:\Harmony\GitHub-OneRepo
python verify_before_push.py
预期：三行文件统计 + 「根目录必备文件: OK」+ [PASS]。这个脚本用自身路径定位，从任意目录用绝对路径跑也可以。

第 2 步：GitHub 网页新建一个空仓库

建议名 smart-inspection-car，选 Public / Private 后，三个初始化选项一个都别勾。复制 HTTPS 地址。

第 3 步：一次 init → add → 核对 → commit

git init
git add .
git status --short
git ls-files | Select-String -Pattern 'ai_config.json|cloud_config.json|devices.json|\.hap|\.p12|\.db'
git commit -m "feat: 智能巡检车 V1/V2/V3 三代源码（脱敏整理）"
预期：约 216 行 A ...；倒数第二条没有任何输出；commit 显示 216 files changed 左右。

第 4 步：绑定并推送

git branch -M main
git remote add origin https://github.com/<你的用户名>/smart-inspection-car.git
git remote -v
git push -u origin main

弹窗时用户名填 GitHub 账号名、密码框粘贴 PAT（ghp_...）。详见上一篇教程第 2 步。

第 5 步：给三代各打一个 tag（可选但推荐）

git tag -a v1.0.0 -m "V1 TCP 直连单车版 · 定版归档"
git tag -a v2.0.0 -m "V2 华为云 IoTDA 云控版 · 冻结基准"
git tag -a v3.0.0 -m "V3 巡检车队平台 · 当前版本"
git push origin --tags
git push 默认不会带 tag，必须单独 git push origin --tags（或 git push origin v1.0.0 逐个推）。tag 是 Git 的概念，Release 是 GitHub 网页的包装，两者不是一回事。

上传后验收

  • 仓库首页显示的是总 README，三代对照表和目录地图正常渲染。
  • 三个子目录都能点进去，各自 README 可见；搜索 ai_config.json / .hap 无任何结果，只能搜到 *.example.json。
  • Commits 里只有 1 条初始提交；Tags 页有 3 个 tag。
  • 只在这一个目录里执行了 git init；GitHub-Ready 那套没有 .git。

7 一个仓库里，三个版本的 Release 怎么分

这是单仓库唯一比三仓库麻烦的地方：所有 Release 都在同一个列表里。解决办法是「tag 前缀 + 附件名前缀 + 发布说明」三件套。

图 2 · 三个 tag 挂在同一条 Releases 列表上，命名必须自带版本号
约定做法
tagv1.0.0 / v2.0.0 / v3.0.0；以后改版用 v3.1.0，不要三个版本都叫 v1.0
Release 标题必须带版本与子目录名，例如「v3.0.0 · V3 巡检车队平台（03-Fleet-V3）」
附件文件名统一前缀：v1-tcp_... / v2-iotda_... / v3-fleet_...
发布说明写清对应哪个子目录、适用 SDK / 板子版本、SHA256、已知限制

网页上挂附件（对每个 tag 做一次）

  1. 仓库页 → Releases → Draft a new release
  2. 在 tag 下拉里选已推送的 v3.0.0（或现场新建同名 tag）
  3. 填标题与说明；把附件拖进去；点 Publish release
  4. 本地先算校验值：Get-FileHash -Algorithm SHA256 .\文件名，把结果贴进说明
tag建议附件说明
v1.0.0可不放；或 v1-tcp_source-snapshot.zipV1 没有必须分发的二进制，纯源码就能跑
v2.0.0可不放；或 v2-iotda_profile.zip产品模型已在 02-Cloud-V2/profile/ 里，附件只是方便取用
v3.0.0v3-fleet_unsigned.hap（未签名）+ 说明 / 截图包别放签名版：绑 UDID 且在实测 API 15 板子上启动崩溃（见上一篇）
Release 附件同样是公开的。不要放 *.p12 私钥、真实 devices.json / cloud_config.json / ai_config.json、以及 E:\Harmony\CompleteProject\V3-Fleet-Complete.zip（含真实密钥的完整包）。想练流程，用源码快照 zip 或截图包最安全。
只想练一次的话：给 v3.0.0 建一个 Release、挂一个 v3-fleet_源码快照.zip（把 03-Fleet-V3 目录压成 zip，注意先确认里面没有真实配置），写清 SHA256 和已知限制就够了。V1/V2 的 tag 保留但不建 Release 也完全没问题。

9 与前后知识点的连接

  • 《把项目上传到 GitHub · 手把手》是「方案 A（三仓库）」的完整命令；本篇是「方案 B（单仓库）」。两篇不冲突，选一套看即可：认证方式、新建空仓库不勾 README、status 肉眼核对、PAT 这些完全通用，只是 init/push 的次数从 3 次变 1 次。
  • 《固件与烧录工具要不要上传》给出「源码 / 成品 / 第三方大件 / 密钥」四分类，本篇把这个分类整个搬进一个仓库：前三类的判定不变，只是成品从「三个仓库各自的 Release」变成「一条 Releases 列表上的三个 tag」。
  • 《项目版本全景与目录盘点》解释了为什么是 V1/V2/V3 三代；单仓库的目录树正是那张演进图的物理落地。
  • 往后：打 tag → 建 Release → 挂附件 → 写校验值，之后可以学 git log -- 路径、git checkout v1.0.0 回到某一代、以及 GitHub 的 Release 说明模板。
  • 回到运行时四层：仓库结构变化不改动任何接口；别人 clone 后仍按各子目录 README 的端口（9000 / 9090 / 8000）启动。

10 自测小问题（点开看答案）

1. 一个仓库放三个版本，会不会让代码互相干扰？

不会。三个子目录各自是独立工作目录，README 与脚本都用相对自身目录的路径（实测无 ../ 跨目录引用，setup.py 用 __file__ 定位，bat 用 %~dp0）。只要先 cd 进对应版本再运行即可。

2. 单仓库比三仓库少了哪些操作？多了哪件事？

少了两套 init / remote / push 和「别推串仓库」的风险；多了两件事：写一份总 README（已备好），以及用 tag 前缀 + 附件名前缀区分三个版本（因为只有一条 Releases 列表）。

3. git push -u origin main 之后，三个 tag 会自动上 GitHub 吗？

不会。tag 要单独推：git push origin --tags。tag 是 Git 的概念，Release 是 GitHub 网页在 tag 之上加的「标题 + 说明 + 附件」包装。

4. 三个版本的 Release 附件怎么命名才不会混？

tag 用 v1.0.0/v2.0.0/v3.0.0，标题带版本与子目录名，附件统一加前缀 v1-tcp_/v2-iotda_/v3-fleet_，发布说明里写清对应目录、适用环境与校验值。

5. 单仓库最大的劣势是什么？

可见性是整个仓库级的：以后若只想公开 V3、把 V1/V2 保持私有，单仓库做不到，得拆历史或另建仓库。三仓库方案在这个场景下更灵活。

6. 想练 Release 上传附件，最安全放什么？

源码快照 zip（压缩前确认不含真实配置）、演示截图包，或未签名 HAP + 已知限制说明。绝不放 *.p12、真实 *_config.json / devices.json、绑定 UDID 的签名 HAP、含密钥的 V3-Fleet-Complete.zip。
