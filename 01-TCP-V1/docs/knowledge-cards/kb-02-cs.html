客户端与服务端

对应项目文件：server/car_server.py、server/test_client.py、APP CarClient.ets

一、为什么这是重点

整个项目从头到尾只干了一件事：让两个程序说话。谁等、谁连、怎么连、连上后消息怎么流动—— 这就是客户端/服务端模型的全部。面试里"说说 C/S 架构""服务端怎么主动推消息"这类题， 你都有亲手写过的代码可以讲。

二、项目案例复盘：谁在等，谁在连

我们的方案：小车端当服务端（等人来连），APP / 测试脚本当客户端（主动去连）。

角色项目中的实现行为
服务端（车）car_server.pybind(0.0.0.0, 8888) → listen → accept，占住端口守株待兔
客户端（APP）CarClient.etsconnect(10.0.2.2, 8888)，主动找上门
客户端（测试脚本）test_client.pyconnect(127.0.0.1, 8888)，开发期替身
客户端（浏览器）car_view.html连 WebSocket 8889，只看不控

为什么让车当服务端？三个理由：① 车部署后 IP/端口固定，适合"等"；APP 是来去匆匆的一方。 ② 真车主控板将来跑的就是这套服务端逻辑——换硬件不换协议。③ 服务端是状态的唯一持有者 （车在哪、多快、多少电都在 Car 对象里），客户端只是状态的消费者。

服务端三步曲（单元 1 最小回声服务器里逐行写过）：

server = await asyncio.start_server(client_handler, HOST, 8888)
# 等价于三步：
# 1. bind   —— 占住 0.0.0.0:8888 这个"门牌号"
# 2. listen —— 开始排队等连接
# 3. accept —— 每来一个客户端，派一个 handler 专门伺候它

连接建立（底层是 TCP 三次握手，由操作系统自动完成，代码里就是一行 connect）后， 双方拥有一条全双工通道——两条独立的数据流，谁都可以随时发。

三、短连接 vs 长连接

短连接长连接
生命周期一次请求/数据交换后就断开建立后长期保持，随用随发
建连开销每次都要三次握手，频繁且贵只付一次建连成本
实时性差（每次都有建连延迟）好（数据随时可达）
服务端资源用完即释，压力小占着连接数和内存
典型场景网页浏览、普通 HTTP API聊天、游戏、实时行情、本项目控车

本项目必须长连接：STATE 要以 100ms 节奏持续推流，指令要随时可发。 如果用短连接，每秒要握手 10 次，且"车主动推状态"根本无法实现（见第五节）。

长连接的代价：假在线。拔网线、进程崩溃时，TCP 不会立刻通知对端——你的连接可能已经死了， 双方还以为活着。解法是心跳：

# 协议里的 PING / PONG：客户端定时发 PING，服务端回 PONG
# 超时没收到 PONG -> 连接已死，触发重连
if text == "PING":
    return ["PONG"]

四、服务端如何主动推送：广播

这是本项目最值得讲透的设计。HTTP 的世界里永远是客户端问、服务端答（拉模式）； 但车的位置每秒变 10 次，"问"太慢也太浪费——我们用推模式：

# 服务端维护一个"在线名单"
clients = set()                # 所有在线 TCP 客户端

async def client_handler(reader, writer):
    clients.add(writer)        # 接入：登记进名单
    ...
    finally:
        clients.discard(writer)  # 断开：移出名单

async def tick_loop():           # 每 100ms 跑一圈
    car.step()                   # 推进运动模型
    frame = (car.state_frame() + "\n").encode()
    for w in list(clients):      # 名单里的人，每人发一份
        try:
            w.write(frame)
            await w.drain()
        except (ConnectionError, RuntimeError):
            dead.append(w)       # 写失败的（已断开）摘除
    for w in dead:
        clients.discard(w)

三个工程细节：

① list(clients) 拷贝后再遍历——遍历过程中集合可能被并发修改，直接遍历原集合会报错；

② 写失败的客户端先收集后摘除——广播循环里不做复杂操作，保持"快进快出"；

③ 一份状态，多路分发：同一个 Car 对象，TCP 客户端收文本 STATE，WebSocket 客户端收 JSON—— 广播循环"一个循环喂两张嘴"。

推 vs 拉不是二选一，是按场景选：实时控车用推（本项目）；低频查数据用拉。 下一阶段（华为云 IoT）你会看到翻转：云平台的设备影子就是拉为主的——到时候回来对照。

五、面试高频问答

Q1：什么是服务端？它和客户端的本质区别是什么？

A：本质区别是谁监听、谁连接：服务端 bind + listen 固定端口等待；客户端主动 connect。 服务端通常还是状态与数据的权威持有者（本项目里车的位置只在服务端），客户端是请求方/展示方。 同一台机器上两个程序可以互为对方的客户端和服务端。

Q2：描述一下从 connect 到数据往返的完整过程。

A：客户端 connect(IP, port) → 操作系统完成三次握手 → 服务端 accept 返回新连接 → 双方拿到同一对"文件描述符级"的通道 → send/recv 全双工收发 → 一方 close（发 FIN）→ 对端 recv 返回空，知道对端下线（我们服务端据此记"正常退出"）。

Q3：服务端怎么把同一条消息发给所有在线客户端？

A：维护在线连接集合（如本项目的 clients = set()），推送时遍历集合逐个 write， 写失败的从集合移除。注意遍历时用副本、异常要兜住——广播循环不能被一个坏连接搞崩。

Q4：一个服务端怎么同时伺候多个客户端？（高频！）

A：三种主流方案：① 每连接一个线程/进程（直观但开销大）；② I/O 多路复用（select/epoll， 单线程监听一堆 socket）；③ 事件循环 + 协程（asyncio 本质是对 epoll 的封装）。 本项目单元 1 是单连接阻塞版（第二个客户端连不进来），单元 2 升级为 asyncio—— 每个连接一个协程，互不阻塞。能亲手对比过这两个版本，是极大的加分项。

Q5：怎么判断长连接是否还活着？

A：应用层心跳（本项目 PING/PONG）或 TCP 自带的 keepalive（默认 2 小时太钝，一般不用）。 心跳超时未回 → 判定假在线 → 断开重连。

六、动手验证与思考题

验证 1：起 car_server.py，开两个终端分别跑 test_client.py——服务端日志出现两个连接， 任一终端发 CMD:FORWARD，两个终端的 STATE 坐标同步变化（广播的直接证据）。

验证 2：手动杀掉一个客户端（Ctrl+C），看服务端日志如何记"正常退出"； 再用任务管理器强杀进程，对比"异常断开"——理解两种断线在服务端眼里的区别。

思考：如果 100 个客户端同时在线，tick_loop 每 100ms 要写 100 次， 其中某个客户端网络很卡（写缓冲堆积），会发生什么？怎么防止"一个慢客户端拖垮整辆车的广播"？ （关键词：写超时、发送队列上限、踢掉慢客户端）
