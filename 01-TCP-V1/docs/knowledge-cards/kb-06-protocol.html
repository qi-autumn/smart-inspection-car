应用层协议设计：粘包、分帧与"消息"的诞生

对应项目文件：car_server.py / test_client.py / CarClient.ets（三处都写了分帧）

一、为什么这是重点（也是马老师没说、但必须补的一点）

这是整个项目含金量最高、面试最区分水平的知识点，我们在课程里前后踩了三次： 服务端单元 2 踩、客户端收 STATE 时踩、APP 的 CarClient.ets 又踩。 它回答一个根本问题：TCP 只负责把字节送到，"一条消息"是应用层自己造出来的概念。

二、核心概念：字节流没有消息边界

假设客户端连续 send 三次：

send("CMD:FORWARD\n")   # 第一次
send("CMD:LEFT\n")      # 第二次
send("CMD:STOP\n")      # 第三次

接收端 recv 到的可能是——

情况recv 一次收到名称
理想CMD:FORWARD\n刚好一帧
拼接CMD:FORWARD\nCMD:LEFT\nCMD:STOP\n粘包（三条并一条）
截断CMD:FORW半包（一条被劈开）
杂交CMD:FORWARD\nCMD:LEF前粘后断

TCP 是字节流协议：它保证字节顺序和不丢不重，但从不保证"你 send 一次 = 对方 recv 一次"。 发送端缓冲、Nagle 合包、接收端读取时机都会改变切割点。100ms 高频推 STATE 的本项目， 粘包几乎必然发生。

三、解法：应用层约定帧边界

本项目的约定：一帧 = 一行文本（UTF-8），以 \n 结尾。 接收端不" recv 一次算一条"，而是把数据攒进缓冲区，按 \n 切：

# 服务端侧（asyncio 自带 readline，一行就是一帧）
line = await reader.readline()          # 读到 \n 才返回

# 客户端侧（test_client.py / CarClient.ets 手工分帧，逻辑完全一致）
buf += data                             # 新到的字节先攒着
while "\n" in buf:                      # 缓冲区里有完整的行吗？
    line, buf = buf.split("\n", 1)      # 切出第一行，剩余留在缓冲区
    handle(line)                        # 逐帧处理

无论 TCP 怎么切割，这个循环都能正确重组出一条条完整的消息—— 半包等下一片凑齐，粘包循环逐条吃掉。理解了这个循环，你就理解了所有流式协议的底层。

其他常见的分帧方案（对比记忆）：

方案原理代表
分隔符（本项目）约定 \n 结尾，按行切Redis、SMTP、行协议
定长帧每帧固定 N 字节嵌入式串口协议、老金融报文
长度前缀帧头先写"正文长度 n"，再读 n 字节HTTP body、MQTT、游戏网络包
自带边界协议层自己定义帧结构WebSocket、消息队列
回看 04 课的伏笔：本项目 WebSocket 侧（俯视图）从不写分帧代码，直接 JSON.parse—— 因为 WebSocket 协议自带帧边界；TCP Socket 侧则三处都要手写分帧。这就是"选不同协议"对代码量的直接影响。

四、我们定了一门"语言"：CMD-STATE 协议

分帧解决"一条消息从哪到哪"，协议解决"消息什么意思"。本项目 8888 端口上的完整语法：

方向帧含义
↑ 客户端 → 车PING心跳探测
↑CMD:FORWARD[:speed] / BACK / LEFT / RIGHT / STOP / STATUS控制指令（速度 0~100，可省略）
↓ 车 → 客户端ACK:FORWARD:70回执：已收到并执行
↓STATE:x=..,y=..,heading=..,speed=..,battery=..状态帧，100ms 广播
↓PONG / ERR:UNKNOWN_CMD:FOO / ERR:BAD_FRAME心跳应答 / 错误帧

四个设计决策，每个都值得在面试里展开：

① 为什么每条指令要 ACK？TCP 的可靠只保证"字节送到了"，不保证"对方理解并执行了"。 ACK 是应用层确认，让 APP 能区分"发了"和"生效了"——可靠控制的最低要求。

② 为什么必须有 ERR 帧？CMD:FOO、BADLINE、CMD:FORWARD:abc 都回 ERR 且服务端永不崩溃。面向网络的程序要假设对面是"不怀好意的小孩"： 非法输入是常态，健壮性是设计出来的。

③ 为什么 PING/PONG？长连接的"假在线"问题（02 课）：TCP 断了不会立刻通知对端， 心跳是主动体检。

④ 坐标契约写死在三处代码的注释里：场地 800×600、(0,0) 左上角、heading 0°=朝上顺时针增—— 协议不仅是消息格式，还包括所有字段的语义约定（见 05 课"三处一致"）。

改协议 = 改两端，还可能改中间。所以单元 4 之后车端"封版"：协议契约一旦冻结， 后续所有单元只消费不修改——这是真实的工程纪律，也是为什么第一个单元就值得把协议想清楚。

五、面试高频问答

Q1：什么是粘包？怎么解决？（超高频）

A：TCP 是字节流，没有消息边界，多次发送的数据可能被合并接收（粘包）或一次数据被截断（半包）。 根因在 TCP 的缓冲与合包机制——本质上 TCP 从来没有"包"的概念，是应用层误以为有。 解法是应用层定界：分隔符（\n）、定长、长度前缀三选一。本项目用 \n 分帧， 接收端维护缓冲区循环切割；APP 端 CarClient.ets 里的实现与服务端完全一致。

Q2：UDP 会有粘包吗？

A：不会。UDP 是数据报协议，天然一次收发一个完整报文（有边界），但不可靠、可能丢包乱序。 经典对比：TCP = 可靠的字节流水管，UDP = 便宜但可能丢的明信片。实时语音/游戏常用 UDP， 宁可丢帧不可延迟。

Q3：为什么不用 JSON 传 STATE？（结合项目答更好）

A：STATE 每 100ms 一帧、字段短小，文本键值对 ~50 字节；JSON 加上字段名和引号要翻倍， 还要序列化/解析开销。控车链路追求轻快，用自定义文本帧；而浏览器俯视图 10Hz 用 JSON ——可读性和开发效率优先。同一项目两种编码并存，本身就是"按场景选格式"的示范。

Q4：TCP 已经可靠了，为什么应用层还要 ACK / 心跳？

A：TCP 可靠的是"传输"：字节不丢不乱。但"对方进程是否活着、是否正确处理"它管不着。 ACK 提供业务级确认（已执行），心跳提供活性探测（假在线检测）——应用层的可靠性要自己负责。

Q5：如果让你重新设计协议，你会改什么？

A：开放题，答出思考深度即可。可选方向：长度前缀替代分隔符（支持二进制/多行正文）； STATE 加单调递增序号（检测丢帧乱序）；CMD 加 requestId（并发指令的回执匹配）； 二进制定长帧（带宽敏感场景）；加版本号字段（协议演进兼容）。

六、动手验证与思考题

验证 1（亲眼看粘包）：起 step2 服务端，用 python 一行命令连续发两条指令不打延时： python -c "import socket;s=socket.create_connection(('127.0.0.1',8888));s.sendall(b'PING\nPING\n');print(s.recv(1024))" ——大概率一次 recv 收到两个 PONG，这就是"两次 send 一次 recv"。

验证 2（半包）：把 sendall(b'PING\nPING\n') 改成 sendall(b'PIN') 再 sendall(b'G\n')——服务端照常回 PONG，因为 readline 会等到 \n 才处理。

思考：STATE 帧里 battery 是 87 而 WS JSON 里是 87.0—— 两个端解析时要不要紧？这说明"字段语义契约"还应包含什么？（类型、精度、取值范围—— 真正的接口文档比语法重要得多。）
