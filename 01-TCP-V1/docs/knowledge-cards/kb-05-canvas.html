Canvas 实时渲染：小车是怎么"活"起来的

对应项目文件：web/car_view_step1.html（静态）→ car_view.html（最终版）

一、为什么这是重点

"页面上的小车怎么画的？怎么动的？轨迹怎么实现的？"——这三个问题背后是前端可视化的一整条技术链： Canvas 坐标系、变换、渲染循环、数据驱动重绘。而且本项目强调的"坐标系三处一致"， 是所有地图 / 游戏 / 图表类应用共有的核心问题。

二、核心概念：Canvas 是"画完就忘"的位图画布

Canvas 和 DOM 元素（div/button）的根本区别：DOM 是保留模式——你声明一个按钮，浏览器替你一直显示； Canvas 是立即模式——你每画一笔只是往一块位图上涂像素，画完浏览器不记得， 想改画面必须整块重画。

这直接决定了本项目俯视图的架构：没有"移动小车对象"这回事，只有"用新坐标把整幅画重画一遍"。

function render() {
  drawGrid();                  // 第 1 层：场地网格
  if (car) {
    drawTrail();               // 第 2 层：历史轨迹
    drawCar();                 // 第 3 层：小车
  } else {
    drawIdleHint();            // 没数据：等待提示
  }
  requestAnimationFrame(render);  // 排队下一帧，循环往复
}

requestAnimationFrame（rAF）让浏览器在"下一次刷新时机"回调 render——通常每秒 60 次。 于是形成双节奏配合：数据 100ms 一帧（WebSocket 推），画面 16ms 一帧（rAF 重绘）。 每次重绘都用全局变量 car 里最新的一份数据——这就是"数据驱动渲染"。

三、小车怎么画：translate / rotate 两步变换

难点：小车是一张"竖着的图"（车头朝上），但它的朝向是任意角度的。 Canvas 的解法是变换坐标系而不是变换图形——口诀：先搬桌子（translate），再转桌子（rotate），最后在桌子上画车：

function drawCar(x, y, heading, color) {
  ctx.save();
  ctx.translate(x, y);              // ① 把原点搬到车中心
  ctx.rotate(headingRad(heading));  // ② 整个坐标系顺时针转 heading 度

  // —— 以下坐标全部是"以车为中心"的本地坐标 ——
  // 约定：车头指向本地 -Y（画布上方）。rotate 之后，本地 -Y 就是运动方向
  ctx.fillStyle = color;
  roundRect(-15, -22, 30, 44, 6); ctx.fill();   // 车身 30×44
  ...
  ctx.restore();   // 恢复变换——下一辆车/下一帧不受污染
}

save()/restore() 是变换的"存档/读档"：进车前存档，画完读档， 保证每辆车的变换互不影响——轨迹、网格才不会被"转花"。

坐标系三处一致（本项目最重要的契约）

位置约定
服务端运动模型x += speed·sin(heading)，y -= speed·cos(heading)——y 取负因为 y 向下为正
浏览器 Canvas天然 (0,0) 左上角、y 向下、rotate 正角度=顺时针——与服务端约定同构，零转换直接画
鸿蒙 APP只显示数字不画图，但解析的 x/y/heading 语义必须相同
为什么 heading=90° 是朝右？顺时针 90°，"上"转到"右"，正对着 Canvas rotate 的正方向。 如果哪一处理解成逆时针（数学角），小车就会"镜像乱跑"——比如发 LEFT 车往右转。 这类 bug 的排查方法论：锁定约定 → 三处逐一核对 → 只改不一致的那一处。

四、小车怎么"动" + 轨迹怎么实现

动：WebSocket onmessage 每 100ms 更新 car = JSON.parse(ev.data)； rAF 下一帧重绘时用新 x/y/heading——小车就"爬"过去了。60fps 重绘 + 10Hz 数据， 视觉上平滑（浏览器在两帧数据间其实是阶梯状跳动的，10Hz 对这种速度已经足够顺眼）。

轨迹渐隐：一个数组 + 一条透明度规则：

var trail = [];                       // 历史足迹
ws.onmessage = function (ev) {
  car = JSON.parse(ev.data);
  trail.push({ x: car.x, y: car.y });       // 每帧记一个点
  if (trail.length > 240) trail.shift();    // 只留最近 24 秒
};
function drawTrail() {
  for (var i = 1; i < trail.length; i++) {
    var alpha = i / trail.length;           // 越新（下标越大）越不透明
    ctx.strokeStyle = "rgba(64,132,220," + (alpha * 0.55) + ")";
    ctx.beginPath();
    ctx.moveTo(trail[i-1].x, trail[i-1].y); // 相邻两点连线
    ctx.lineTo(trail[i].x, trail[i].y);
    ctx.stroke();
  }
}

三个设计点：① 轨迹只是"历史位置的折线图"，没有任何魔法；② shift() 控制长度， 防止数组无限膨胀；③ alpha 随下标线性增强 → 老的足迹自然淡出。

断线自动重连：onclose 里 setTimeout 2 秒后重连，配合 car = null 回到"等待画面"—— 服务端重启后页面自动跟上，不用手动刷新。

五、面试 / 实操问答

Q1：Canvas 和 SVG 怎么选？

A：Canvas 是立即模式位图，适合大量、高频重绘的元素（游戏、粒子、本项目的实时小车）； SVG 是保留模式矢量图，每个图形都是可交互的 DOM 节点，适合少量、需要点击/缩放的图（图标、流程图）。 本项目 60fps 重绘，SVG 每帧改 DOM 反而低效，选 Canvas 正确。

Q2：requestAnimationFrame 和 setInterval(16) 的区别？

A：rAF 与浏览器刷新周期同步、页面切后台自动暂停（省资源）、一次回调正好渲染一帧； setInterval 不看渲染时机、后台照跑、可能堆积回调。动画一律 rAF。

Q3：页面动画掉帧，可能的原因？

A：每帧做了重活——大循环、强制布局回流、大量 DOM 操作、每帧新建对象触发 GC。 本项目的做法可借鉴：数据解析只在 onmessage（10Hz），渲染循环里只有纯绘制； 轨迹限长 240 点，绘制量恒定。

Q4：为什么画面要"全屏重画"而不是只重画小车？

A：Canvas 立即模式没有"局部对象"概念，旧像素不会被自动清除。重画前先 drawGrid 覆盖全屏 等效于清屏。进阶做法（脏矩形/离屏 Canvas/分层）只在性能不够时才需要——先做对，再优化。

六、动手验证与思考题

验证 1：打开 car_view_step1.html 拖动 heading 滑块——确认 90° 朝右、345° 是左转一格 （和服务端 CMD:LEFT 的 -15° 互相印证）。

验证 2：在 drawCar 的 ctx.rotate(headingRad(heading)) 前加一个负号， 重启页面连上服务端发 LEFT——复现"镜像乱跑"。这是理解"约定一致性"最直观的方式。 （改完记得改回来！）

思考 1：把 TRAIL_MAX 从 240 改成 24000 会怎样？改成 3 呢？——理解"保留多少历史"是体验与开销的折中。

思考 2：APP 端将来如果也要画俯视图（ArkTS 同样有 Canvas 组件），坐标代码能照搬吗？ 哪些约定必须一字不差？（答：坐标系约定全部照搬——这正是它写进三处代码顶部注释的原因。）
